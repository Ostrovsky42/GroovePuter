# 0.9.9-E2b — canonical rhythm diff / mutation budget

## Purpose

Freeze one deterministic, bounded **canonical-relative** material diff and
mutation-budget validation contract.

Given canonical material `C` and candidate material `V`, E2b answers:

```text
C + V + existing archetype/policy context
    -> E2c RhythmMutationDelta sequence
    -> observational stats
    -> existing MutationBudget legality
    -> existing rhythm_realizer structural legality
```

The first argument is always the canonical material. There is no API taking a
`previousVariant`, accumulated mutation history, lifecycle state or candidate
cache. Repeated locally legal mutations therefore do not reset the budget: a
final candidate is measured again from `C`.

E2b does **not** generate candidates, choose candidates, schedule attempts,
implement KEEP/REVERT/EVOLVE, persist history, own a graph, or use Song/Phrase
transport state.

## API

Header:

```text
src/generation/rhythm/rhythm_canonical_diff.h
```

Primary functions:

```cpp
CanonicalRhythmDiffStatus canonicalRhythmBarDiff(
    const RhythmArchetype& archetype,
    const RhythmBarPlan& canonical,
    const RhythmBarPlan& candidate,
    BarFunction function,
    TransformationIntent intent,
    RhythmMutationDelta* deltas,
    uint16_t deltaCapacity,
    CanonicalRhythmDiffStats& stats);

bool canonicalRhythmBudgetValid(
    const MutationPolicy& policy,
    RealizationLevel level,
    TransformationIntent intent,
    const CanonicalRhythmDiffStats& stats);

CanonicalRhythmCandidateValidation canonicalRhythmCandidateValid(
    const RhythmArchetype& archetype,
    const RhythmPhrasePlan& canonical,
    const RhythmPhrasePlan& candidate,
    uint8_t barIndex,
    RealizationLevel level,
    BarFunction function,
    TransformationIntent intent,
    RhythmMutationDelta* deltas,
    uint16_t deltaCapacity);
```

`CanonicalRhythmDiffStats` is observational data only. It is not a budget and
contains no policy permissions. `MutationPolicy`, `MutationBudget`,
`MutationFlags` and `allowedIntents` remain authoritative.

`canonicalRhythmCandidateValid()` permits only the selected `barIndex` to
differ. This prevents a caller from hiding an unmeasured phrase mutation in a
second bar while validating one bar's budget.

## Canonical material interpretation

E2b compares `RoleRhythmPlan::{structural,secondary,ghosts,accents}` on the
existing 16-step grid. Gate masks are not a new mutation class; the existing
`rhythmMutationPlanValid()` remains responsible for gate, lane, density,
anchor, protected-space and hard-relationship correctness.

Literal interpretations:

| Canonical -> candidate | E2b delta |
|---|---|
| same material | zero deltas (`KEEP` material case) |
| regular onset disappears | `DROP` |
| new non-ghost onset | `ADD` |
| new ghost onset | `GHOST` |
| same onset coordinate, accent changes | `ACCENT` |
| same-kind onset moves to an E2c-legal same-lane target | `DISPLACE` |

E2b intentionally does not synthesize a `KEEP` record for every unchanged hit.
`KEEP` is the zero-delta material result; emitting all unchanged onsets would
turn a diff into a full material copy and waste bounded RAM.

A same-coordinate structural/secondary/ghost class conversion fails closed as
`UnrepresentableDelta`. E2c deliberately has no conversion operation, and its
GHOST contract is a new onset on an empty site.

## DROP + ADD versus DISPLACE

Matching is bounded and deterministic; it is not graph matching.

For each `RhythmRole` in ordinal order:

1. pair exact same-kind onsets at the same logical step;
2. visit each unmatched canonical source in logical step order `0..15`;
3. visit unmatched same-kind candidate targets in logical step order `0..15`;
4. accept the first pair for which
   `rhythmMutationDisplacementGrammarLegal()` returns true;
5. unmatched canonical sources become `DROP`;
6. unmatched candidate regular/secondary onsets become `ADD`;
7. unmatched candidate ghosts become `GHOST`;
8. exact same-coordinate accent differences become `ACCENT`;
9. output is sorted with E2c `rhythmMutationDeltaLess()`.

Consequences:

- radius is exactly E2c `kDisplaceRadius == 2`;
- there is no step-15 -> step-0 wrap;
- displacement is same-lane because E2c has one `RhythmRole` field;
- protected/forbidden/anchor displacement rules are not duplicated: E2b asks
  `rhythmMutationDisplacementGrammarLegal()`;
- a distance-3/4 local trajectory does not become one canonical displacement;
  it remains canonical `DROP + ADD` and must pass those budgets instead.

## Existing budget interpretation

E2b counts:

```text
adds
secondaryAdds (subset of ADD)
ghostAdds
drops
displacements
accentChanges
```

The existing fields remain the limits:

```text
maxAdds
maxDrops
maxDisplacements
maxAccentChanges
maxSecondaryAdds
maxGhostAdds
flags
allowedIntents
```

The Stage 14.1 / E1a compatibility rules are preserved:

- explicit `maxSecondaryAdds` wins; otherwise secondary additions use the
  legacy `maxAdds` path when `AllowOptionalAdds` is set;
- explicit `maxGhostAdds` wins; otherwise ghosts use the legacy `maxAdds` path
  when `AllowGhostConversion` is set;
- P3 with no direct ghost budget retains the existing cumulative P2 ghost
  allowance;
- ordinary DROP requires the existing preferred-drop permission; Reduce/Break
  contexts may use their existing transformation permission;
- DISPLACE requires `AllowOptionalDisplace`;
- ACCENT requires `AllowAccentVariation`;
- concrete `TransformationIntent` must be present in `allowedIntents`.

No aggregate mutable counter is carried from a previous candidate.

## Canonical-relative laundering regression

With a one-ADD policy:

```text
C -> A : + step 4                 => one ADD, locally legal
A -> B : + step 8                 => one ADD, locally legal
C -> B : + step 4 + step 8        => two ADDs, ILLEGAL
```

Equivalent tests exist for DROP, DISPLACE, ACCENT, GHOST and a mixed case.

For DISPLACE specifically:

```text
C: step 4
A: step 6    C->A distance 2      => DISPLACE, legal
B: step 8    A->B distance 2      => DISPLACE, locally legal

C->B distance 4                   => not DISPLACE
                                    => canonical DROP + ADD
```

A displacement-only budget rejects `B`. Intermediate variants cannot reset the
canonical diff because the E2b validation surface contains no previous-variant
or history input.

## Existing musical ownership

E2b does not reimplement final music validity.

`canonicalRhythmCandidateValid()` delegates both canonical and candidate phrase
plans to:

```text
rhythmMutationPlanValid()
```

Therefore existing rhythm_realizer / relationship_resolver ownership remains
responsible for:

- archetype lane identity;
- immutable/canonical anchors;
- protected spaces;
- forbidden structural destinations;
- lane/density bounds;
- gate derivation;
- hard lane relationships.

DISPLACE source/target grammar remains E2c
`rhythmMutationDisplacementGrammarLegal()` ownership.

## V0 handoff

V0 remains research/tooling only.

V0 may call E2b with canonical material, candidate material and the existing
archetype/level policy context and consume the returned delta/stats/legal result.
V0 must **not** reproduce matching, budget, anchor or relationship semantics.

Ownership split:

```text
E2b  canonical-relative legality
V0   graph enumeration / measurement only
```

E2b adds no production graph, adjacency cache or lifecycle owner.

## Troubleshooting

If an ADD/DROP/ACCENT/GHOST laundering test becomes legal, do not increase the
budget fixture. Check that validation still compares the original canonical bar
against the final candidate.

If a radius/wrap test becomes DISPLACE, check E2c `kDisplaceRadius` and
`rhythmMutationDisplacementGrammarLegal()` before changing E2b matching.

If anchor/protected/forbidden/relationship rejection changes, fix the existing
realizer/relationship contract or its delegation. Do not add a parallel music
validator inside E2b.

If `OutputTooSmall` appears, provide a larger caller-owned delta buffer or use
stats-only mode (`nullptr`, capacity `0`). E2b does not allocate a hidden buffer.
