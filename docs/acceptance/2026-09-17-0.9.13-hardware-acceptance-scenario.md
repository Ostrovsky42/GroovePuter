## 1. Boot / basic liveness

After reboot, UI appears, keyboard/encoders respond, no reset loop, no
stuck notes or hung audio.

## 2. BPM ownership — primary scenario

Open a project at a known BPM (e.g. 120). Enable external clock/SEQ MASTER at
a different tempo (e.g. 137), play, stop, wait for autosave, reboot.

**Expected:** the project shows 120 again; 137 could only drive playback
during external follow and must not persist into the scene.

Code evidence: `setExternalClockBpm()` writes only `bpmValue`
(`src/dsp/miniacid_engine.cpp:724-731`); `setBpm()` writes `projectBpmValue`
first and derives `bpmValue` from it (`:712-721`); `syncSceneStateToManager()`
persists `projectBpmValue`, never `bpmValue` (`:3168`). `projectBpmValue` has
exactly one read site in the whole engine — that sync call — confirmed by
exhaustive grep.

**Fixed, was a correction here:** `bpm()` returns `bpmValue`
(`:745`), and every page that displays tempo reads `mini_acid_.bpm()`.
`setExternalClockBpm()` never touched `projectBpmValue`, and nothing resynced
`bpmValue` back after Stop or after switching the clock source away from
external, so the engine kept rendering at the last followed tempo until the
next explicit `setBpm()` or a reboot — not just a stale display, an actually
wrong render tempo if the musician resumed internal playback without touching
BPM. `MiniAcid::restoreProjectBpm()` now runs exactly once, at the moment
`ExternalClockBlockResult::sourceChanged` is true and the new source is not
`SeqtrakExternal` (`GroovePuter.ino`, right after `processBlock()`). RED->GREEN
verified: temporarily reverted `restoreProjectBpm()` to a no-op, confirmed
`tests/test_bpm_ownership.cpp` fails on `closeEnough(engine.bpm(), 120.0f)`,
restored, confirmed green. The on-screen BPM should now revert immediately on
Stop, not only after reboot.

## 3. Material lifecycle on the real pages

On Pattern Edit and Synth Sequencer, create a NEXT candidate, then check:

- Alt+Enter performs ACCEPT, not GO;
- a queued GO disarms on plain Escape while NEXT is kept;
- plain Escape on a ready (non-queued) NEXT removes that NEXT;
- on-screen text is product language (`NEXT READY`, `GO DISARMED: NEXT KEPT`),
  not internal G4 diagnostics.

Code evidence: `isGoEvent()`/`isCancelEvent()` explicitly reject Alt/Ctrl/Meta
(`src/ui/material_development_ux.h:31-47`); `handleCancel()` disarms a queued
GO without clearing NEXT, and otherwise cancels NEXT (`:110-120`);
`test_material_development_command_routing.cpp` exercises this through the
real `PatternEditPage`/`SynthSequencerPage` `handleEvent()`, not just the
free-function helpers (`:13-14, 90-113`).

**Correction — Alt+Backspace/Alt+X is not "discard NEXT":** it is DISCARD of
CURRENT — `discardCurrentMaterial()` reverts Working back to the accepted
canonical Pattern and clears lineage/anchor state, but never touches
`pendingMaterial_[idx].queued` (`src/dsp/miniacid_engine.cpp:4509-4580`). The
routing test proves this is the intended behavior, not an oversight: right
after dispatching Alt+Backspace it asserts
`engine.hasPendingMaterial(0)` is still true
(`tests/test_material_development_command_routing.cpp:104-106`). If a NEXT
READY indicator is still showing right after Alt+X, that is correct,
tested behavior — a stale NEXT bound to a since-discarded basis will fail
closed on the next GO attempt rather than activate silently, but the
indicator itself does not disappear. Do not log this as a failure.

## 4. Musical transformations

On two- and four-bar material, check HOLD and phrase growth: no shortening,
no overlap, no runaway note duration at the phrase boundary. For
REVOICE/MOVE with a register shift, a candidate with a broken melodic
contour must be rejected, never reaching NEXT.

Code evidence: HOLD clamps extension to the phrase end
(`src/dsp/musical_development.h:289-300`); growth rejects a target shorter
than the source (`:567-575`) and rejects on event-capacity overflow before
returning (`:599-604`); `growWorkingMaterial()` checks `dev.success` before
ever calling `prepareNextMelody()` (`src/dsp/miniacid_engine.cpp:4372-4376`);
the contour gate rejects REVOICE/HOLD/CONNECT/MOVE candidates with
`contourPreserved == Fail` before NEXT (`src/dsp/musical_development.h:400-414`,
commit `18beaf63`).

## 5. MIDI / transport smoke

Internal play -> external clock follow -> Stop. Check for no stuck notes, no
false ownership, no unintended BPM persistence.

Code evidence: a clock-source change is detected inside
`ExternalMidiClockFollower::processBlock()` and forces
`ExternalTransportCommand::Stop` on the very next block
(`src/midi/external_midi_clock_follower.h:47-59`); `GroovePuter.ino` maps
that to `pauseTransport()` (`:131-140`); `pauseTransport()` clears retrigger
state and live notes before returning (`src/dsp/miniacid_engine.cpp:563-579`).
So switching clock source during play does produce an explicit stop with
note cleanup — this is real code, not an assumption. Explicit handoff
(seamless continuation across sources) is still a separate, unimplemented
product risk; today's safe behavior is exactly the stop this scenario
expects, not silent desync.

Start with point 2 — it directly proves the most dangerous fixed defect.
