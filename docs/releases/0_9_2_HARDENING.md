# GroovePuter 0.9.2 — Current Release Hardening

Status: **development / feature freeze**

Base: `dev_0.9.2`

## Purpose

0.9.2 hardens the current 0.9.x product before sampler recovery begins in 0.9.3.
It is not a feature release.

Allowed scope:

- release blockers and hardware regressions;
- Song/pattern lifecycle defects in already-shipped workflows;
- persistence, storage, memory and transport correctness;
- small UX/help changes needed to make existing behavior usable and diagnosable;
- acceptance and regression tests.

Out of scope:

- sampler recovery or sampler redesign unless a sampler defect blocks 0.9.2 runtime stability;
- new arranger architecture;
- new synth engines;
- new generation ownership models unrelated to a current-release defect.

## P0 — Song generated-pattern lifecycle

### Problem

Song generation materializes new pattern data into the resident pattern page. A page has
`2 banks x 8 slots = 16 slots` per editable track. The project address space is larger
(`16 pages x 16 slots = 256 global pattern IDs`), but only one pattern page is resident
in RAM at a time.

Before 0.9.2 hardening, the Song allocator only accepted a slot when its pattern bytes
were physically empty and no Song A/B row referenced it. Removing a Song cell cleared
the reference but left the generated bytes intact. The slot therefore stayed unusable
until a project-wide clear. Repeated generation of one occupied cell could also consume
new slots through copy-on-write.

### 0.9.2 lifecycle contract

- A Song-generated pattern is explicitly marked as Song-owned.
- The marker uses one already-reserved `unused` step bit; Scene size and the raw `.gpp`
  page layout do not grow.
- Legacy/manual/imported non-empty patterns have no Song-owned marker and are never
  reclaimed automatically.
- Re-generating a uniquely referenced Song-owned cell reuses its current slot in place.
- A shared Song-owned pattern remains copy-on-write; other rows and the other Song slot
  keep their source pattern unchanged.
- Clearing a Song cell removes only its arrangement reference. Pattern bytes are not
  immediately erased, so the existing immediate Undo path does not lose material.
- An unreferenced Song-owned pattern is an orphan and may be reclaimed by a later Song
  generation operation.
- Failed multi-track generation remains transactional: no partial row writes.

### Pattern-page boundary

The lifecycle fix does not pretend that all 256 pattern IDs are resident in RAM. When a
resident page has no empty or reclaimable slot for a track, the page is full. Existing
pattern-page navigation (`Alt+[` / `Alt+]`) remains the safe control-side way to move to
another page; Song references already store global page-aware IDs and playback uses the
existing deferred page-switch path.

Automatic cross-page allocation is allowed in 0.9.2 only if it can reuse that existing
control-side paging lifecycle without scanning SD or performing storage I/O in the audio
callback. Until that is proven, the release must prefer an explicit page-full condition
over unsafe synchronous page scans.

## P1 — UX / diagnostics

P1 for this defect is intentionally small:

- document that Song deletion frees the arrangement reference and generated orphan
  material becomes reusable;
- make pattern-page capacity and page-full recovery discoverable;
- keep `Alt+[` / `Alt+]` as the explicit pattern-page control unless safe automatic
  overflow is implemented and tested;
- do not require `Clear Project` merely to recover Song-generated orphan capacity;
- preserve manual/imported patterns and existing Song A/B semantics.

## Build / flash

Cardputer ADV release build uses the existing project build path and normal 0.9.x
hardware configuration. No wiring or peripheral changes are introduced by this stage.

Run the repository host suite before hardware flash:

```bash
bash tests/run_host_tests.sh
```

Then build/flash the normal Cardputer ADV target using the same pinned Arduino/M5Stack
dependencies as CI.

## Expected behavior

On the Song page:

1. Generate a cell with `G`.
2. Repeatedly regenerate that same uniquely-owned generated cell.
3. The Song pattern reference must stay on the same slot rather than consuming a new
   slot for every reroll.
4. Clear the generated Song cell with the existing cell-clear action.
5. Generate another cell after the page would previously have become exhausted.
6. An unreferenced Song-generated orphan may be reused; a non-empty manual/imported
   pattern must never be overwritten.
7. If the resident page is genuinely full of referenced/manual material, switch pattern
   page with `Alt+]` and continue on a free page rather than clearing the project.

## Troubleshooting

If Song generation still reports no available slot:

- check whether the current pattern page is genuinely full of referenced or manual data;
- switch to another pattern page with `Alt+[` / `Alt+]`;
- verify that the failing material was created by Song generation; manual/imported
  patterns are deliberately protected from automatic reclaim;
- do not use `Clear Project` as normal pattern-pool maintenance.

## Acceptance checklist

### Host

- [ ] `test_song_pattern_materializer` passes.
- [ ] unique generated reroll keeps the same global pattern reference.
- [ ] shared generated source uses copy-on-write.
- [ ] deleted generated orphan can be reclaimed.
- [ ] non-empty manual/imported material cannot be reclaimed.
- [ ] referenced empty slot cannot be overwritten.
- [ ] generator failure leaves Scene and dirty revision unchanged.
- [ ] full Core regressions pass.
- [ ] SDL build passes.
- [ ] Cardputer ADV normal + fixed-DRAM build passes.
- [ ] Cardputer ADV SEQTRAK MIDI-only build passes.

### Cardputer ADV

- [ ] Generate one Song cell, then reroll it at least 20 times; it must not burn through
  20 pattern slots.
- [ ] Generate several cells, clear some generated cells, then generate again; no
  `Clear Project` should be required to reuse reclaimable generated capacity.
- [ ] Share one generated pattern between two rows; reroll one row and verify the other
  row is unchanged.
- [ ] Put a manual pattern in an otherwise unreferenced slot; Song generation must not
  overwrite it.
- [ ] Fill the current resident page legitimately, switch with `Alt+]`, generate on the
  next free page, and play across the page boundary.
- [ ] Save, reboot, load, and repeat the lifecycle smoke test.

## Hardware assumptions

- M5Stack Cardputer ADV / ESP32-S3.
- Existing 0.9.x SD-card project/pattern storage.
- No new wiring, voltage, I2C, SPI or MIDI hardware requirement.
- No sampler acceptance belongs to this stage unless a sampler fault is classified as a
  release blocker.
