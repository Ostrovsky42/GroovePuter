# 0.9.9-E2a — canonical rhythm mutation producer

## Purpose

Add the first production consumer of the frozen E2c `RhythmMutationDelta`
contract: one bounded deterministic producer that answers **which one-hop,
bar-local mutation deltas may be proposed**.

E2a does not execute a selected delta and does not decide whether an evolution
attempt should happen. It does not make the candidate set a production variant
graph.

Exact base:

```text
agent/20260824-02-0.9.9-e2c-mutation-delta-contract
c595ee78f5a72e7e963658475fb1dd31d14da4f3
```

## Ownership

`rhythm_realizer` remains the single mutation owner.

```text
Phrase / Bar planning
        |
        v
rhythm_realizer
  produceRhythmMutationCandidates()   <- E2a proposal only
  applyRhythmBarFunctionMutation()    <- existing E1a executor
        |
        v
materialization / live bridge
```

No second generator is added to `bar_evolution`, PhraseEvolution, the live
bridge, or materialization.

## Inputs

`RhythmMutationProducerRequest` contains:

- `archetype`
- canonical rhythm material
- current rhythm material
- bar index
- role mask
- planned `BarFunction`
- planned `TransformationIntent`
- `RealizationLevel`
- `GenerationContext`

The producer is bar-local. It neither reads nor derives a physical Pattern
address.

`GenerationContext` is part of the stable call contract, but E2a does no
stochastic pruning, ranking, cadence decision or candidate selection. Therefore
it does not use generation coordinates to reorder or choose proposals.

## Outputs

```cpp
RhythmMutationProducerResult produceRhythmMutationCandidates(
    const RhythmMutationProducerRequest& request,
    RhythmMutationDelta* output,
    uint16_t capacity);
```

The caller owns the output buffer. E2a allocates no candidate container and
stores at most:

```text
min(capacity, kMaxRhythmMutationDeltasPerBar)
```

`truncated=true` means more structurally possible proposals existed than fit in
the supplied buffer. The stored values are always the canonical-order prefix.

`KEEP` is never emitted as a candidate or graph self-edge. An empty candidate
set is a valid outcome.

## Determinism

Candidate enumeration is direct and stable:

1. `RhythmRole` ordinal;
2. logical step `0..15`;
3. frozen E2c operation ordinal;
4. DISPLACE target `0..15`.

No unordered container iteration and no architecture-dependent sort participate.
The focused test compares the emitted corpus between GCC and Clang and reruns
the same request for exact field-wise equality.

## Operation corpus

### Current production reference policy

The current `ReferenceVocabulary` policy factually enables:

| Level | Proposed operation classes |
|---|---|
| P1 | none (`KEEP` is not a candidate) |
| P2 | `GHOST` |
| P3 | `ADD` plus the existing cumulative P2 `GHOST` permission |

Current reference policy does **not** enable `DROP`, `DISPLACE`, or `ACCENT`.
E2a does not fabricate those production candidates merely to populate the
vocabulary.

### Contract fixture

A focused synthetic fixture enables the already-existing mutation flags and an
explicit `AnchorTransformRule` to exercise all frozen E2c values as contracts:

- `KEEP`: verified as a semantic value that is never emitted;
- `ADD`;
- `DROP`;
- `DISPLACE`;
- `ACCENT`;
- `GHOST`.

The fixture is test evidence for the producer API, **not** a claim that the
current production reference vocabulary enables every operation.

`Reduction` / `Break` are the only existing BarFunction executor paths treated
as destructive transformation permission. `Turnaround` is not treated as DROP:
its current E1a behavior adds late ghost cues.

Canonical-source DROP requires a matching existing
`AnchorTransformRule::suppressibleCanonical`. Canonical-source DISPLACE uses the
unchanged E2c `rhythmMutationDisplacementGrammarLegal()` rule and therefore
requires `displaceableCanonical`.

## Boundary: E2a vs E2b

E2a may reject structurally impossible proposals using lane grammar, protected
spaces, immutable/canonical ownership, density headroom and hard relationship
safety.

E2a does **not** read these numeric budget fields:

```text
maxAdds
maxDrops
maxDisplacements
maxAccentChanges
maxSecondaryAdds
maxGhostAdds
```

Those are not per-hop quotas for this producer.

In particular, this sequence is intentionally **not** made legal by E2a:

```text
canonical
  -> current variant containing one mutation
  -> another locally possible E2a proposal
```

The second proposal may still be emitted. E2b must compare the resulting
material to canonical material and decide total canonical-relative legality and
budget. E2a does not reset a budget at each hop.

## Boundary: E2a vs E2t / lifecycle

E2a does not answer **when** evolution may be attempted. It consumes no Activity
or cadence state and does not use `generationAttemptOrdinal` as cadence
ownership.

E2a adds no KEEP/REVERT/EVOLVE lifecycle, persistence, history, candidate cache,
scheduler state, or transport ownership.

## Variant graph boundary

The E2a candidate list is proposal tooling input only. It is not an authoritative
variant graph. Graph authority remains deferred until the later canonical
ADD/DROP/DISPLACE/ACCENT/GHOST semantics and E2b legality are frozen and rerun.

## Troubleshooting

If GCC and Clang corpus differs, do not add sorting by pointer/address or relax
ordering assertions. Find the architecture-dependent input or iteration order.

If an E2c test fails, do not change operation ordinals, delta shapes,
DISPLACE radius, same-lane/bar-local/non-wrapping semantics, or canonical order
inside E2a.

If the source contract detects numeric budget fields inside E2a producer code,
move that accounting to E2b rather than renaming the fields or hiding the read.

If a canonical anchor proposal appears without the matching explicit transform
rule, treat it as an ownership regression.

If the current production corpus starts emitting DROP/DISPLACE/ACCENT, first
audit the reference policy change. Do not update the E2a expectation silently.
