# 0.9.9-E2c — canonical rhythm mutation delta contract

## Purpose

Freeze one bounded, bar-local mutation vocabulary for the next E2a producer
and E2b diff/budget checkpoints without changing production musical output.

The authoritative owner remains `rhythm_realizer`.
`bar_evolution` remains trajectory / BarFunction planning only.

Frozen vocabulary:

```text
KEEP
ADD
DROP
DISPLACE
ACCENT
GHOST
```

This checkpoint does not add mutation lifecycle state, Activity, a production
variant graph, or a second mutation executor.

## Exact E1a assumptions

Starting point:

```text
610e5dc2bde665bab5ee6e68ee484af7192d2952
```

This is the exact E1a production candidate. Characterization PRs #344 and #349
are evidence only and are not ancestry for E2c.

The exact E1a representation is:

- 16 logical steps per bar;
- eight `RhythmRole` lanes;
- `RoleRhythmPlan::{structural,secondary,ghosts,accents}`;
- lane grammar spaces
  `immutableAnchors / canonicalAnchors / preferred / optional / forbidden`;
- existing `MutationBudget` and `MutationFlags`;
- `AnchorTransformRule::displaceableCanonical` as the existing explicit
  canonical-source displacement permission.

## Frozen delta representation

`RhythmMutationDelta` is deliberately bar-local:

```text
operation
role
sourceStep
targetStep
```

There is one role field, so `DISPLACE` cannot express a cross-lane move.

`kNoMutationStep == 0xFF`.

| Operation | Source | Target | Meaning |
|---|---|---|---|
| `KEEP` | step | same step | onset stays at the same coordinate |
| `ADD` | none | step | non-ghost onset is added |
| `DROP` | step | none | onset is removed; removing a ghost is still `DROP` |
| `DISPLACE` | step | different step | same-lane move |
| `ACCENT` | step | same step | accent state changes without topology change |
| `GHOST` | none | step | a new ghost onset is added |

`GHOST` is intentionally not modeled as an attribute conversion. The exact E1a
production realizer adds ghost onsets on empty sites, and the #344
characterization records ghost additions.

`ACCENT` freezes only the delta shape. E2c does not add accent mutation to
production; current `addVariation()` remains secondary/ghost addition only.

## Deterministic canonical ordering

Valid deltas sort by:

1. `RhythmRole` ordinal;
2. logical step `0..15` (`sourceStep`, or `targetStep` for source-less ADD/GHOST);
3. `RhythmMutationOp` ordinal;
4. `sourceStep`;
5. `targetStep`.

Mask bit order is not used for ordering.

## DISPLACE contract

```text
kDisplaceRadius = 2
```

Distance is bar-local absolute logical-step distance. There is no wrap:
`15 -> 0` is not a radius-1 displacement.

`rhythmMutationDisplacementGrammarLegal()` freezes coordinate/anchor legality.
A displacement target must be in the same lane's `preferred` or `optional`
space and must not be forbidden, protected, immutable, or canonical.

An immutable source is never movable.

A canonical source is movable only when a matching existing
`AnchorTransformRule` has the same role, BarFunction and TransformationIntent
and explicitly contains the source in `displaceableCanonical`.

E2c only freezes this grammar-level permission. It does not wire DISPLACE into
`applyRhythmBarFunctionMutation()` or relax the current plan validator.

## Existing budget ownership

E2c does not add a cost field, budget enum or parallel permission flags to
`RhythmMutationDelta`.

The existing `MutationBudget` remains authoritative, including:

```text
maxAdds
maxDrops
maxDisplacements
maxAccentChanges
maxSecondaryAdds
maxGhostAdds
flags
allowedIntents
```

This is intentional. Budget accounting is contextual today: for example,
secondary/ghost additions have explicit-budget and legacy fallback behavior,
while BarFunction reduction/break also clears ghost ornaments outside the
topological drop loop. E2c would be overreaching if it invented a new
context-free budget class for those cases.

E2a/E2b must therefore use this exact delta vocabulary plus the existing
`MutationBudget` / `MutationFlags` and source/result plan context. Introducing a
second budget hierarchy is a contract violation.

## Fixed bounds

The contract freezes:

```text
kMaxRhythmMutationDeltasPerBar    = 256
kMaxRhythmMutationDeltasPerPhrase = 1024
sizeof(RhythmMutationDelta)        = 4
```

These are absolute representation ceilings, not an instruction to allocate a
1024-entry production buffer. E2a/E2b should remain budget-bounded.

`GenerationDomain::BarEvolution` is compile-time guarded at numeric value `12`.

## Troubleshooting

If the C++ contract test fails, do not relax the expected operation ordinals,
source/target shapes, ordering, radius, or `BarEvolution=12` silently. Treat
that as a contract change requiring explicit review.

If the source contract reports that `RhythmMutationDelta` appears in production
implementation files, E2c has crossed into E2a implementation scope.

If the Stage 6.1 matrix fails, treat it as a regression in the existing E1a
owner/executor behavior. Do not update characterization output in E2c.
