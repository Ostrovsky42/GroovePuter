# RB-301 — audition ownership and output spike

**Base:** `d77c00c50f7e66b8bb0714723ad2d3e0a23dfdc3`, accepted source `85b53e6b77bd167c23cf23fd78e0832ba9e6a0ef`. This is a bounded design/source audit and host routing test. Browser audition, its UI, persistence and hardware acceptance are **not implemented or proven** by this document.

## Existing playback route

The existing `MiniAcid::processSequencerEvents` (`src/dsp/miniacid_engine.cpp`, around 2779–2911) advances the existing tick clock, handles BAR_START, and reads the drum set for timing before calling `triggerDrumVoice_`. That trigger reads the pending or accepted drums again, applies drum automation, mute/probability/step FX, and calls the drum voice. `activeDrumPattern` also reads the pending set for retriggers and display cache. A transient substitution must be coherent at **all** these read sites; replacing only the initial hit test would mix timings, velocities or retriggers from different patterns.

`PatternPublishingDrumVoice::triggerPattern` (`src/dsp/pattern_drum_event_tap.h`) uses the existing Drums output ownership for INTERNAL/MIDI/LAYER and publishes PatternPlayer drum events to `MusicalEventQueue`. The existing queue applies MIDI output ownership; the MIDI dispatcher uses `PatternDrumGateScheduler` for sample-timed release and routes through the existing device profile. Sampler `triggerPad` independently checks the internal drum output permission (`src/sampler/drum_sampler_track.cpp`). This supports reusing the current route rather than adding a sequencer or sending MIDI from the UI. Existing legacy `SourceClass::Preview` is not a substitute: its legacy default excludes MIDI.

`triggerDrumVoice_` returns when the current Song drums address is negative. Until a safe target contract is implemented, audition there must refuse visibly rather than fabricate a slot. Song advancement and pending generation are ordered at BAR_START; a preview must validate the **post-transition** address and owner, including row/page/project and Scene revision. Pattern groove and automation must continue to come from the accepted context rather than scratch defaults. No added allocation, I/O, catalog scan, Scene serialization or waiting belongs in the audio callback.

## Ownership conflict and bounded direction

The current `QuantizedGenerationDetail::g_slots[2]` owner (`src/generation/migration/quantized_generation_commit_impl.h`) stores prepared/old-audible data for **already committed** generation. Its lease policy refuses a new writer when any slot is occupied. `pendingAudibleDrumPatternSet` (`quantized_generation_undo_owner_impl.h`) only exposes a Full-generation old snapshot. At BAR_START `commitQuantizedGenerationAtBarStart` requires a committed revision, clears the slot and invokes `barrierPatternRuntimeSourceTransition`, which barriers both synths. That lifecycle cannot be used unchanged for a persistent, uncommitted drum preview: releasing the candidate at its first bar or barriering Synth A/B would violate the Browser contract.

The narrow direction to test next is to extend the **existing publication ownership**, not add a transport or scheduler: reserve mutually exclusive typed preview states alongside generation, retain an immutable active drum candidate, prepare the next candidate on the control side, and swap at the existing BAR_START after target/revision checks. With only two slots, a candidate already pending makes another writer BUSY or requires explicitly tested coalescing; never overwrite a slot the audio task may still read. Generation/other publication owners must receive a typed conflict, with no committed mutation. Cancel/STOP/page/project changes must retire previews without exposing stale pointers, restore the accepted route and clean Pattern drum MIDI gates without barriering user synths. The exact lifetime protocol and whether both existing slots can serve it must be proven by concurrency and boundary tests before wiring UI.

Follow-up host test `testUncommittedAuditionIsNotGenerationActivation` exercises the actual generation owner: a second ordinary lease is refused even when only one slot is being written; a Full-scope published candidate also exposes Synth A; and BAR_START rejects and retires that candidate when its committed revision is zero. The Scene revision remains unchanged in this test. These results confirm that merely repurposing the current API is unsafe; they do not prove that a new preview lifecycle is safe. The shared slots are also used by Song and Phrase activation, so the reader lifetime, atomic reservation across all owners, and cancellation protocol need a coherent design before production wiring. This is the specified RB-301 architecture-conflict stop; no audio or UI implementation is claimed.

The focused C++ activation executable passes with this test after updating its outdated fake engine declarations. The enclosing `tests/run_generation_0_9_9_c_tests.sh` does **not** pass: its existing Python source regression expects an absent `if (keyF)` anchor. The remaining commands in that script therefore did not run in this check.

SOLO is a further unresolved ownership requirement: temporarily suppress only the intended sequenced synth audio **and MIDI** without rewriting user mute state or silencing unrelated live notes. WITH SONG must retain accepted synth playback. Tab may use the existing transport, but starting/stopping an audition must preserve whether the user was already playing. These are requirements, not behavior already implemented.

## Memory evidence

The ELF from the `d77c00c5` Cardputer build has SHA-256 `3884792b15c1ef66c2eed9da17146f0dd573f9a626121d698e5a9e71d76cfe56`. Xtensa `nm -S` reports `QuantizedGenerationDetail::g_slots` at `0xE80` = 3,712 B total for two existing slots, `g_slotState` 2 B, `g_publishedSlot` 1 B and `g_audioMutationGate` 12 B. The build reports static DRAM 185,788 / provisional 191,488 B, margin 5,700 B; the threshold itself has outstanding policy items. The separate RB-1 target probe measured `Workspace=1,416 B`, `Candidate=1,208 B` and the factory's own frame 752 B, while the called materializer has a 1,536 B frame. These are not a whole-stack peak or a device measurement.

For scale only, allocating a new permanent workspace plus two full Candidates would add 3,832 B before state and other changes, reducing the arithmetic margin to 1,868 B. No such allocation has been made or accepted. Reusing the existing slots may avoid additional full-pattern storage but requires the ownership redesign and conflict proof above. The control-side workspace may instead have a bounded lifetime; device stack/heap/timing and final linked DRAM must still be measured.

Reproduce slot sizes with `xtensa-esp32s3-elf-nm -S --size-sort build/cardputer-adv-current/GroovePuter.ino.elf` using the installed M5Stack Xtensa toolchain; see `docs/testing/2026-11-06-rhythm-browser-catalog-checkpoint.md` for the candidate target-size and individual-frame measurements.
