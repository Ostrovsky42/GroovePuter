# RB-301 — audition ownership and output spike

**Base:** `d77c00c50f7e66b8bb0714723ad2d3e0a23dfdc3`, accepted source `85b53e6b77bd167c23cf23fd78e0832ba9e6a0ef`. This is a bounded design/source audit and host routing test. Browser audition, its UI, persistence and hardware acceptance are **not implemented or proven** by this document.

## Existing playback route

The existing `MiniAcid::processSequencerEvents` (`src/dsp/miniacid_engine.cpp`, around 2779–2911) advances the existing tick clock, handles BAR_START, and reads the drum set for timing before calling `triggerDrumVoice_`. That trigger reads the pending or accepted drums again, applies drum automation, mute/probability/step FX, and calls the drum voice. `activeDrumPattern` also reads the pending set for retriggers and display cache. A transient substitution must be coherent at **all** these read sites; replacing only the initial hit test would mix timings, velocities or retriggers from different patterns.

`PatternPublishingDrumVoice::triggerPattern` (`src/dsp/pattern_drum_event_tap.h`) uses the existing Drums output ownership for INTERNAL/MIDI/LAYER and publishes PatternPlayer drum events to `MusicalEventQueue`. The existing queue applies MIDI output ownership; the MIDI dispatcher uses `PatternDrumGateScheduler` for sample-timed release and routes through the existing device profile. Sampler `triggerPad` independently checks the internal drum output permission (`src/sampler/drum_sampler_track.cpp`). This supports reusing the current route rather than adding a sequencer or sending MIDI from the UI. Existing legacy `SourceClass::Preview` is not a substitute: its legacy default excludes MIDI.

`triggerDrumVoice_` returns when the current Song drums address is negative. Until a safe target contract is implemented, audition there must refuse visibly rather than fabricate a slot. Song advancement and pending generation are ordered at BAR_START; a preview must validate the **post-transition** address and owner, including row/page/project and Scene revision. Pattern groove and automation must continue to come from the accepted context rather than scratch defaults. No added allocation, I/O, catalog scan, Scene serialization or waiting belongs in the audio callback.

## Ownership conflict and bounded direction

The current `QuantizedGenerationDetail::g_slots[2]` owner (`src/generation/migration/quantized_generation_commit_impl.h`) stores prepared/old-audible data for **already committed** generation. Its lease policy refuses a new writer when any slot is occupied. `pendingAudibleDrumPatternSet` (`quantized_generation_undo_owner_impl.h`) only exposes a Full-generation old snapshot. At BAR_START `commitQuantizedGenerationAtBarStart` requires a committed revision, clears the slot and invokes `barrierPatternRuntimeSourceTransition`, which barriers both synths. That lifecycle cannot be used unchanged for a persistent, uncommitted drum preview: releasing the candidate at its first bar or barriering Synth A/B would violate the Browser contract.

The narrow direction to test next is to extend the **existing publication ownership**, not add a transport or scheduler: reserve mutually exclusive typed preview states alongside generation, retain an immutable active drum candidate, prepare the next candidate on the control side, and swap at the existing BAR_START after target/revision checks. With only two slots, a candidate already pending makes another writer BUSY or requires explicitly tested coalescing; never overwrite a slot the audio task may still read. Generation/other publication owners must receive a typed conflict, with no committed mutation. Cancel/STOP/page/project changes must retire previews without exposing stale pointers, restore the accepted route and clean Pattern drum MIDI gates without barriering user synths. The exact lifetime protocol and whether both existing slots can serve it must be proven by concurrency and boundary tests before wiring UI.

Follow-up host test `testUncommittedAuditionIsNotGenerationActivation` exercises the actual generation owner: a second ordinary lease is refused even when only one slot is being written; a Full-scope published candidate also exposes Synth A; and BAR_START rejects and retires that candidate when its committed revision is zero. The Scene revision remains unchanged in this test. These results confirm that merely repurposing the current API is unsafe; they do not prove that a new preview lifecycle is safe. The shared slots are also used by Song and Phrase activation, so the reader lifetime, atomic reservation across all owners, and cancellation protocol need a coherent design before production wiring. This is the specified RB-301 architecture-conflict stop; no audio or UI implementation is claimed.

The first follow-up implementation adds an inactive control-side reservation of both existing slots. A partial reservation is rolled back; existing ordinary generation leases cannot be acquired while both slots are reserved. It has no caller, no audio reader, no candidate publication and no cancellation during playback. Tests exercise the real slot owner, including refusal and rollback, but do not prove concurrent preview lifetime, Song/Phrase behavior or audio safety. Before this primitive is used by a Browser session, its release contract must be extended to establish session identity and audio-reader quiescence; the current release is valid only for the reserving control owner before any candidate is exposed. Do not connect it to playback as-is.

Subsequent bounded work adds session IDs, staging into the reserved slots, audio-side activation at a caller-provided bar boundary, and termination requiring audio quiescence. A host test checks stable active bytes until activation, stale-session refusal, bounded queue behavior and 5,000 control/audio publication cycles. This remains an **unwired primitive**: its caller must hold the existing AudioMutationGate for termination, ensure one control producer and one audio consumer, validate the project/target/revision after Song advancement, and preserve accepted groove/automation. The test exercises concurrent publication but is not proof of all interleavings, physical timing, MIDI cleanup, or context invalidation. ThreadSanitizer could not start in this environment (`unexpected memory mapping`). Playback integration must establish those contracts before use.

The latest owner tests bind a session to an engine, target, revision, Song mode/slot/row and drum address. A supplied mismatching context invalidates the session permanently until control-side teardown; an absent drum address refuses admission. Candidate staging copies accepted automation lanes and groove into the prepared set. These checks still depend on a future real playback caller capturing the right context and calling validation after Song advances; the test's fake engine does not establish integration behavior. `begin` and `end` require audio quiescence, and invalidated sessions must still be ended to release slots.

The follow-up engine slice connects a control-side API and the existing bar boundary to the three drum reads (step timing, trigger and retrigger). It does not wire Browser UI. The full SDL-source host test `tests/run_rhythm_browser_engine_tests.sh` passed against the real engine: one staged kick was observed in the existing PatternPlayer MIDI queue, a second candidate remained pending until the next bar, accepted drum data and selected synth notes stayed unchanged, and STOP prevented the session from resuming. This does not establish full Song/Phrase scenarios, complete Synth A/B equivalence, physical MIDI/audio, or output cleanup. In particular, STOP and context invalidation currently invalidate the session but leave its reserved slots until the control owner calls `endRhythmAudition` under AudioGuard; cleanup must be integrated before Browser exposure. Drum MIDI gate cleanup across swap/cancel and all lifecycle exits also remain open. No hardware acceptance is implied.

The next cleanup slice emits the existing target-scoped Drums MIDI barrier on candidate activation and explicit end, clears pending drum retriggers, and schedules invalidated sessions for UI-thread teardown under AudioGuard. The real-engine test checks the cleanup mask contains Drums only, STOP cleanup releases slots and a new session can begin. The test does not simulate the physical MIDI dispatcher, verify every lifecycle exit or establish seamlessness under a changing Song. The earlier full host run failed at link because it compiled the engine and UI from different intermediate revisions while this work was changing; it is not valid evidence for the committed code and must be repeated against an immutable snapshot.

The real-engine test now also publishes a one-note Phrase on Synth A and confirms the Phrase is active while audition drums are active. It exercises automatic Song advancement from row 0 to row 1 on the existing bar boundary, verifies that the row-0 audition is invalidated rather than redirected, and services its cleanup. This deliberately conservative behavior ends audition when the Song row changes; continuous audition over a changing Song arrangement is not yet implemented or accepted. These are host tests, not listening or physical MIDI evidence. `tests/run_host_tests.sh` now invokes the engine test for future regressions.

Follow-up: Song audition can continue over an automatic row change when the rows resolve to the same drum address, even if synth selectors change. The original destination remains pinned; the first row using a different drum address invalidates the preview. A real-engine test exercises three consecutive rows (drums 0, 0, 1), checking continuation and then cancellation. Continuous audition across different drum addresses remains unimplemented; future Apply must independently validate its pinned destination and may not assume the current Song row is the original one. No change to persisted Song is made by this lifecycle.

Later follow-up: audition now continues across resident Song rows with different drum addresses. The original session context remains pinned for the future Apply contract; a missing drum address, page/project change, revision change or Song ownership change invalidates it. The drum automation read while auditioning comes from the currently accepted row, not the candidate prepared for an earlier row. The real-engine test checks rows 0, 0, 1, empty, including the new row's reverb automation and safe cancellation on empty. This does not prove physical timing, nonresident-page transitions, or a future Apply implementation. Apply must validate the original destination independently of the currently playing Song row.

The real-engine host test now compares the entire Scene object byte-for-byte before and after a pattern-mode preview/cancel, with active drum automation disabled in the fixture, and checks both Scene revision fields and a pre-existing Undo receipt's type, direction and payload. It also exercises invalidation after a simulated load-revision change and page-loading flag, followed by control-side slot release. Log `rb-preservation.log` SHA-256 `7bc7f534360a0f3540c4175a7c622fd9e98ed165afdf77b0db8d83a8ac5c7113` is stored in the local evidence archive. The engine host test also looks up and materializes vocabulary archetype 401 with a fixed seed, stages it against an empty accepted pattern, and observes drum NoteOn events through the real PatternPlayer MIDI queue over one bar. The focused C++ activation executable passes with this test after updating its outdated fake engine declarations. The enclosing `tests/run_generation_0_9_9_c_tests.sh` does **not** pass: its existing Python source regression expects an absent `if (keyF)` anchor. The remaining commands in that script therefore did not run in this check.

SOLO is a further unresolved ownership requirement: temporarily suppress only the intended sequenced synth audio **and MIDI** without rewriting user mute state or silencing unrelated live notes. WITH SONG must retain accepted synth playback. Tab may use the existing transport, but starting/stopping an audition must preserve whether the user was already playing. These are requirements, not behavior already implemented.

## Memory evidence

The ELF from the `d77c00c5` Cardputer build has SHA-256 `3884792b15c1ef66c2eed9da17146f0dd573f9a626121d698e5a9e71d76cfe56`. Xtensa `nm -S` reports `QuantizedGenerationDetail::g_slots` at `0xE80` = 3,712 B total for two existing slots, `g_slotState` 2 B, `g_publishedSlot` 1 B and `g_audioMutationGate` 12 B. The build reports static DRAM 185,788 / provisional 191,488 B, margin 5,700 B; the threshold itself has outstanding policy items. The separate RB-1 target probe measured `Workspace=1,416 B`, `Candidate=1,208 B` and the factory's own frame 752 B, while the called materializer has a 1,536 B frame. These are not a whole-stack peak or a device measurement.

For scale only, allocating a new permanent workspace plus two full Candidates would add 3,832 B before state and other changes, reducing the arithmetic margin to 1,868 B. No such allocation has been made or accepted. Reusing the existing slots may avoid additional full-pattern storage but requires the ownership redesign and conflict proof above. The control-side workspace may instead have a bounded lifetime; device stack/heap/timing and final linked DRAM must still be measured.

Reproduce slot sizes with `xtensa-esp32s3-elf-nm -S --size-sort build/cardputer-adv-current/GroovePuter.ino.elf` using the installed M5Stack Xtensa toolchain; see `docs/testing/2026-11-06-rhythm-browser-catalog-checkpoint.md` for the candidate target-size and individual-frame measurements.
