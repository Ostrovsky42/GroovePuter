# LOOPER — дизайн (без кода)

Статус: дизайн, код не менялся. База: ветка `exp/looper` от `1ecd4688` (src идентичен `fec3237c`).
Исходные данные: `docs/research/LOOPER_RESEARCH.md`. Метки: **[код]** — проверено в коде (file:line),
**[предп.]** — предположение/решение дизайна, требующее проверки на устройстве.

Зафиксированные решения владельца: два слоя в архитектуре, один в v1; looper заменяет PARTNER в меню
(код партнёра остаётся); настройки BARS 1/2/4, LENGTH, CHANNEL, EVOLVE 0–3 (по умолчанию 0), без REPLACE,
с HOLD; overdub + один уровень undo + только сетка; вывод только MIDI; без free-режима.

## 0. Ключевые решения (кратко)

| # | Решение | Почему |
|---|---|---|
| D1 | Looper — **отдельный объект** `Looper`, а не 5-й режим `CallResponseListener` | Партнёр не трогаем ни строкой. Режим слушателя был бы дешевле (+136 Б), но правит `call_response_listener.h` и тянет его ловушки: `stopClock()` стирает петлю [код] `call_response_listener.h:429-443`, REPLACE [код] `:235-248`, монофонный `echoLine` [код] `call_response_performance_plan.h:102-112` |
| D2 | Воспроизведение через **существующий `ResponsePlayer` партнёра**, взятый по публичному `callResponseListener().responder()` [код] `call_response_listener.h:85` | Свой плеер = +~408 Б (32 × 12 Б слотов) и не влезает в цель +200 Б. Партнёр скрыт и всегда `Off`, его плеер простаивает. Это заём, не правка: файлы партнёра не меняются. Цена — взаимоисключение (см. §6, R12) |
| D3 | Слой пишется **прямо в пул событий**, без `PhraseCapture` | Свой `PhraseCapture` = +396 Б [код] `call_response_phrase_capture.h:245-251`. Для looper-а окно — это проход петли, онсет известен в момент NoteOn; нужна только таблица «открытых» нот |
| D4 | Один **пул на 32 события** с индексом слоя в каждом событии (2 бита) | 32 = ёмкость плеера [код] `call_response_planner.h:103` и `call_response_responder.h:158`: план прохода никогда не обрезается. Второй слой — 0 Б данных. Отклонение от «отдельной памяти слоя» — см. §3.4 |
| D5 | **Undo без снимка**: биты NEW/SHADOW в старших битах pitch/velocity (оба 7-битные) | Снимок = +130 Б. Биты = 0 Б, undo побайтно точен, заодно **CLEAR тоже отменяем**. Один уровень, общий для всех слоёв |
| D6 | Ёмкость **32 для любого BARS** | Хранилище всё равно 32; лимит 16 у партнёра — наследие фазы 0 [код] `call_response_phrase_capture.h:73-75`. При наложении 1–2 тактов 16 кончаются за 2–3 прохода. Решение владельца было «16 или 32» — предлагаю 32 везде, 0 Б |
| D7 | PLAY проекта **не стирает** слой; Space-стоп останавливает петлю, Space-старт её возобновляет с такта проекта | §2 |
| D8 | HOLD = **замок слоя** (punch-out + запрет REC/DUB/UNDO/CLEAR/BARS), в фазе 2 — ещё и заморозка вариации EVOLVE | §1.5. Критика: в v1 без EVOLVE HOLD — только предохранитель |
| D9 | Управление — **простые клавиши Z / C / V / B / Del** на живой поверхности PERFORM | Свободны [код] `perform_page.cpp:950-1008`, `miniacid_display.cpp:845-880`; цифры заняты mute-ами [код] `miniacid_display.cpp:857-877` |

## 1. UX

### 1.1 Состояния

```
              Z                      downbeat (PLAY) / 1-я нота (часы PERFORM)
   IDLE ────────────▶ ARMED ───────────────────────────────────────▶ RECORD
    ▲  ◀──── Z / C ─────┘                                              │
    │                                         конец прохода (BARS)     │ Z во время REC = «потом DUB»
    │ Del (CLEAR)                    ┌─────────────────────────────────┤
    │ V после REC                    ▼                                 ▼
    └────────────────────────────  PLAY ◀──────── Z ────────────────▶ OVERDUB
                                    │  ▲                                │
                              C, X, │  │ C (или Space-старт,           │ C, X, Space-стоп
                         Space-стоп ▼  │  если остановлен Space-ом)     ▼
                                   STOPPED ◀────────────────────────────┘
   HOLD — флаг поверх PLAY / STOPPED (не отдельное состояние): B вкл/выкл.
```

| Состояние | Что звучит | Что пишется | Выход |
|---|---|---|---|
| IDLE | ничего | ничего | Z → ARMED |
| ARMED | ничего (под PLAY — проект) | ничего; пред-нота за 30 % шага до downbeat станет шагом 0 [код] `call_response_phrase_capture.h:191-199` | downbeat → RECORD; Z/C → IDLE |
| RECORD | живая игра (как всегда) | всё сыгранное, онсет к 1/16 | конец прохода → PLAY (или OVERDUB, если во время REC нажат Z); V → откат в IDLE; C → STOPPED с записанным |
| PLAY | слой + живая игра | ничего | Z → OVERDUB сразу; C → STOPPED |
| OVERDUB | слой + живая игра | новые ноты в слой; каждый проход с нотами = единица undo | Z → PLAY сразу (punch-out); B → PLAY+HOLD |
| STOPPED | ничего | ничего | C → PLAY; Z → PLAY+OVERDUB с ближайшего downbeat |
| +HOLD | как PLAY/STOPPED | ничего, всё изменяющее заблокировано | B снимает |

Принципы:
- **Z = «ещё запись», V = «выбросить последнее», C = «звук петли вкл/выкл».** Ни одна из Z/C/V не
  уничтожает данные без возможности вернуть (V отменяет и CLEAR).
- **Punch-in/out — сразу, без ожидания downbeat.** Ноты всё равно квантуются к 1/16; ожидание такта в
  наложении — лишняя задержка. Ожидание есть только при старте записи с пустого слоя (ARMED).
- **Старт записи под PLAY — с ближайшего такта, не с кратного BARS** [предп.]: при BARS 4 ждать до 4 тактов
  слишком долго. Фаза петли относительно тактов проекта запоминается (0..BARS-1 тактов, 1 байт), чтобы после
  Space-рестарта петля встала на ту же позицию формы.
- **Часы PERFORM (без PLAY):** запуск первой нотой в ARMED (как у партнёра [код] `call_response_listener.h:172-175`),
  темп = BPM проекта; часы **не останавливаются**, пока слой не пуст (у партнёра — стоп после 2 пустых окон
  [код] `:251-257`, риск R4 исследования).

### 1.2 Клавиши (живая поверхность PERFORM)

Свободные простые клавиши: `Z C V B M` и `Del` на живой поверхности. Буквенные ряды QWERTYUIOP / ASDFGHJKL —
ноты [код] `performance_keyboard.cpp:21-22`; N, X, `\`, `-`, `=`, `,`, `.` заняты [код] `perform_page.cpp:950-1008`;
цифры 1–0 — глобальные mute [код] `miniacid_display.cpp:857-877`; Alt/Ctrl/Fn — глобальные (keys.md).

| Клавиша | Действие | Почему эта |
|---|---|---|
| `Z` | REC / DUB (IDLE→ARM, PLAY↔DUB, STOP→DUB, в REC — «потом DUB») | крайняя левая в нижнем ряду, легко найти не глядя |
| `C` | PLAY / STOP петли | рядом с Z |
| `V` | UNDO (один уровень; в RECORD — отмена записи) | рядом |
| `Ctrl+Z` | то же, что V, если у looper-а есть что отменять; иначе прежнее поведение | на PERFORM Ctrl+Z сейчас ничего не отменяет — страница его не принимает [код] `perform_page.cpp:885`, `undo_ux.h:33-38` («UNDO: EMPTY/NOT HERE»). Глобальная лексика «Ctrl+Z = отмена» сохраняется |
| `B` | HOLD вкл/выкл | рядом, но не соседний с Z |
| `Del` (Backspace) | CLEAR (отменяемо через V) | далеко от нот; в слое TOOLS Backspace остаётся «предыдущий контекст» [код] `perform_page.cpp:920`, поэтому CLEAR только на живой поверхности |
| `X` | PANIC: живые ноты + петля → STOPPED, **слой сохраняется** | у партнёра X забывает петлю [код] `call_response_listener.h:96-102`; для своей записи это потеря работы. CLEAR — явно |
| `M` | резерв: выбор/mute слоя 2 (фаза 3) | |

Риск: Z/C/V/B под A/S/D/F/G — промах по ноте нажмёт Z/C. Смягчение: ни одна из них не разрушительна
(Z в PLAY начнёт DUB — V отменит). Проверить на устройстве (§ план, D-тесты).

В слое PERFORMANCE TOOLS буквы Z/C/V/B не перехватываются `handleToolKey` и доходят до живого switch
[код] `perform_page.cpp:582-626`, `:932` — работают и с открытым меню.

### 1.3 Меню PERFORM > INPUT (вместо строк PARTNER 8–13)

| Строка | Значение | `</>` / ENTER | Подсказка (≤ 37 симв.) |
|---|---|---|---|
| 8 `LOOPER` | `IDLE` / `ARM` / `REC 1/2` / `PLAY 2/2` / `DUB` / `STOP` (+` HOLD`) | ENTER = Z | `Z REC/DUB  C PLAY/STOP  V UNDO` |
| 9 ` BARS` | `1 BAR` / `2 BARS` / `4 BARS`; при непустом слое — серым | цикл; при слое — тост | `</> 1/2/4 BARS  CLEAR LOOP TO CHANGE` |
| 10 ` CHANNEL` | `DX ROUTE` / `CH1..16` | цикл | `</> DX=PERFORM DX ROUTE OR CH1..16` |
| 11 ` LENGTH` | `100%` / `75%` / `50%` / `25%` | цикл | `</> PLAYBACK NOTE LENGTH (NOT SAVED)` |
| 12 ` HOLD` | `OFF` / `ON` / `N/A` (пустой слой) | ENTER/`</>` = B | `B: LOCK LOOP - NO REC/UNDO/CLEAR` |
| 13 ` EVOLVE` | **фаза 2**; в v1 строки нет | | `0 EXACT  1 FORM  2 DEVELOP  3 FREE` |

Строка PARTNER скрыта; слушатель партнёра остаётся `Off` (код и тесты целы). Все настройки looper-а —

длины — смена LENGTH обратима.

### 1.5 HOLD

Что это: **замок записанного материала**. Одна клавиша `B` (и строка 12 меню), снимается ею же.

| Где нажат B | Эффект |
|---|---|
| PLAY / STOPPED | HOLD ON: Z, V, Ctrl+Z (looper), Del, смена BARS → тост `HOLD: B TO UNLOCK`, ничего не меняется. C и X работают (это не изменение слоя) |
| OVERDUB | **punch-out сейчас** + HOLD ON. Ноты этого прохода остаются, undo для них сохраняется до снятия HOLD |
| RECORD | HOLD «взведён»: чип `REC>HOLD`; по концу прохода → PLAY+HOLD |
| ARMED / IDLE | тост `NOTHING TO HOLD` |
| HOLD ON | HOLD OFF; состояние PLAY/STOPPED не меняется |

Отображение: второй чип `HOLD` (инверсия, `palette.secondary` — не красный/оранжевый, чтобы не путать с записью),
полоса прохода **без заливки** (только контур и плейхед-линия) — «застывшая» петля, футер `[B]UNLOCK`.

Развитие:
- **Фаза 2 (EVOLVE):** HOLD дополнительно **замораживает вариацию** — проход, звучавший при нажатии B,
  повторяется точно (как HOLD MOTIF у партнёра [код] `perform_page.cpp:569`). Тут HOLD становится
  музыкальным инструментом: «поймал удачную вариацию — держу».
- **Фаза 3 (два слоя):** HOLD — флаг **слоя** (бит в заголовке слоя). «Остановить запись нового слоя, не
  трогая текущий»: держу слой 1 (HOLD), переключаюсь на слой 2, пишу/стираю его свободно.

Критика: в v1 (EVOLVE нет, слой один) HOLD — только предохранитель от случайных Z/Del при игре поверх.
Это полезно (клавиши Z/C рядом с нотами), но не музыкально. Стоит 1 бит. Альтернатива «HOLD = петля
продолжает звучать при уходе со страницы / Space-стопе» отвергнута: два смысла у одной клавиши.

## 2. Что делает PLAY проекта с петлёй

| Событие | Вариант A (**рекомендуется**) | Вариант B «петля = дорожка» | Вариант C «петля независима» |
|---|---|---|---|
| Space-старт | PLAY/«остановлен Space-ом» → проход заново с такта проекта (фаза петли сохранена); RECORD → откат прохода, ARMED на ближайший такт; OVERDUB → punch-out, PLAY | то же | петля продолжает на часах PERFORM, PLAY лишь пересинхронизирует на ближайшем downbeat |
| Space-стоп | PLAY/OVERDUB → STOPPED с флагом «возобновить по Space» (NoteOff сразу) | → STOPPED; звучит только под PLAY | бесшовно переходит на часы PERFORM, звучит дальше |
| Слой | никогда не стирается часами; только Del | то же | то же |
| Без PLAY | работает на часах PERFORM | **не работает** (нужен PLAY) | работает |

Обоснование A:
- **Space = «весь звук стоп».** Нажал стоп — тишина, включая внешний синт. Вариант C нарушает это
  ожидание (стоп нажат, MIDI-петля играет), а единственный способ остановить её вне PERFORM — уйти обратно.
- **Space-старт возвращает петлю на такт 1** с ударными — главный сценарий: записал риф на часах
  PERFORM, включил проект, петля в такт с барабанами.
- **Слой переживает часы** — убирает главную ловушку LOOP партнёра (исследование, вывод 4).
- B проще, но запрещает looper без проекта (а запись без PLAY — частый сценарий скетча). Можно включить
  как опцию позже: это одно условие в `service()`.

Остальные «эпохи»:
- **Смена темпа:** часы PERFORM продолжают позицию непрерывно [код] `call_response_listener.h:218-224`
  (копируем приём); под PLAY — цепочка сетки с ресинхронизацией вне ±½ шага [код] `:310-317`, `:453-461`.
- **Смена BARS:** при непустом слое запрещена (тост). Пустой — сразу, ARMED пере-взводится. Удвоение
  1→2→4 с копированием — фаза 2.
- **Уход со страницы PERFORM** (`IPage::onExit` [код] `ui_core.h:354`): RECORD → проход дописывается
  как есть и закрывается (→ PLAY); OVERDUB → punch-out; ARMED → IDLE. Дальше: **под PLAY петля звучит
  на любой странице** (записал бас — пошёл крутить синты), **на часах PERFORM → STOPPED** (не оставляем
  невидимый звук, который нечем остановить, кроме возврата). Правило для пользователя: «вне PERFORM петля
  звучит только вместе с PLAY».
- **Live-input epoch** (смена источника ввода): главный цикл отменяет плеер [код] `GroovePuter.ino:1244-1248`;
  looper остаётся в своём состоянии, следующий проход стартует по сетке (потеря хвоста одного прохода).

## 3. Модель данных и память

### 3.1 Событие (4 Б)

```
struct LoopNote {
  uint8_t onsetLayer;  // биты 0..5: онсет 0..63 (шаг 1/16 в проходе); 6..7: слой 0..3 (v1: 0)
  uint8_t length;      // 0 = нота ещё держится (не играется); 1..64 шагов, ≤ конца прохода
  uint8_t noteFlag;    // биты 0..6: высота (входная, до Smart Play); бит 7: NEW
  uint8_t velFlag;     // биты 0..6: velocity 1..127; бит 7: SHADOW
};
```

- `NEW` — нота записана в текущей единице undo. `SHADOW` — нота скрыта (замещена или стёрта CLEAR),
  восстанавливается undo.
- Высота — **входная** (что нажато), как отдаёт наблюдатель [код] `performance_input_observer.h:7-18`,
  `performance_keyboard.cpp:1531-1539`. Открытый вопрос Q2 (Smart Play).

### 3.2 Пул и операции

`LoopNote notes_[32]` — все слои. Таблица открытых нот `OpenNote open_[8]` по 3 Б: `tag` (uint16, как у
партнёра: клавиша или `performanceExternalInputTag` [код] `performance_input_observer.h:24-30`) + индекс
в пуле (бит 7 = «затакт следующего прохода»). Сопоставление NoteOff — **только по tag**: NoteOff от
клавиатуры несёт уже интерпретированную высоту [код] `performance_keyboard.cpp:1594`, по высоте искать нельзя.

| Операция | Правило |
|---|---|
| NoteOn (REC/DUB) | онсет = round(pos − passStart) по правилу затакта [код] `call_response_phrase_capture.h:191-199`; онсет = W (затакт) → шаг 0 следующего прохода (петля круговая). Первая запись в новой единице undo → **commit** предыдущей. Видимая нота с той же высотой **и тем же онсетом** в этом слое → SHADOW (или удалить, если она NEW). Пул полон → нота не пишется, `dropped++`, FULL |
| NoteOff | по tag: length = round(pos) − (passStart + onset), min 1, ≤ W − onset |
| Конец прохода | открытые ноты (кроме затакта) закрываются длиной до конца прохода, их поздний NoteOff игнорируется (как в захвате партнёра [код] `call_response_phrase_capture.h:22-24`) |
| commit | снять NEW, удалить SHADOW (уплотнение, переиндексация `open_`) |
| UNDO | удалить NEW, снять SHADOW, выкинуть из `open_` удалённые; `undoValid = false`. Redo нет |
| CLEAR | все видимые ноты слоя → SHADOW (после commit предыдущей единицы); единица undo = CLEAR. Ёмкость освобождается на следующем commit |
| План прохода | видимые (не SHADOW, length > 0) ноты слоёв без mute → `ResponseNote{step=onset, length, note, vel}` 1:1; одинаковая высота с перекрытием → длина ранней обрезается до онсета поздней (иначе MIDI NoteOff одной режет другую); затем LENGTH через `applyAnswerLength` [код] `call_response_planner.h:254-258`. Без `echoLine`, без сворачивания в 24..71 |

Единица undo: **проход RECORD**, **проход OVERDUB, в котором была хоть одна нота** (пустой проход не
трогает undo — лениво: commit только при первой записи), **CLEAR**. Почему проход, а не вся DUB-сессия:
ошибка обычно в последнем проходе, а сессия из 8 проходов целиком — слишком крупная потеря [предп.; если
владелец ждёт RC-505-поведения «отмена всего дубля», это одна строка: commit при входе в DUB, а не при
первой ноте прохода].

Почему держащиеся ноты (`length = 0`) не попадают в план: затакт-нота, нажатая перед downbeat, уже
записана на шаг 0 следующего прохода и звучит вживую — плеер не должен ударить её второй раз поверх.

### 3.3 Память (DRAM, статика)

| Поле | Байт |
|---|---|
| vptr (`PerformanceInputObserver`) | 4 |
| `notes_[32]` | 128 |
| `open_[8]` × 3 | 24 |
| часы: `anchorSteps_` (double), `lastPosition_` (float), `anchorMicros_`, `sixteenthMicros_`, `transportEpoch_`, `lastBlockSequence_`, `gridMicros_` (uint32), `passStart_` (int32) | 8 + 4 + 20 + 4 = 36 |
| состояние: count, state, bars, phaseBars, channel, length, layerFlags (HOLD/mute), activeLayer, source, dropped, флаги (undoValid, resumeOnPlay, dubAfterRec, holdAfterRec), passCount (uint16) | ~12 |
| **Итого** | **≈ 204 Б** (`static_assert(sizeof(Looper) <= 208)`) |

- Объект — `static` в функции `looper()` (как `callResponseListener()` [код] `call_response_listener.h:504-507`) → .bss.
- План прохода (`ResponsePlan`, 131 Б) — **на стеке главного цикла** в `serviceLooper()`; вызывается после
  `serviceCallResponseLog()` (а не внутри), поэтому пик стека — максимум из двух, не сумма.
- Плеер — заимствован (0 Б). Захват — не нужен (0 Б).
- Цель «≤ +200 Б» на грани: если сборка покажет > 200, режем `open_` до 6 (−6 Б) и `lastPosition_` → защиту
  монотонности через `passStart_` (−4 Б). Партнёрские фазы показали, что выравнивание секций часто
  поглощает десятки байт (PHASE5: +0 Б при росте sizeof [код-док] `CALL_RESPONSE_PHASE5_LOOP_GRID.md:129-130`).
- Сейчас 186236 / 191488, свободно 5252 Б.

### 3.4 Два слоя: как архитектура их допускает

- Индекс слоя — в каждом событии (2 бита, до 4 слоёв). Флаги слоя (HOLD, MUTE) — по биту в `layerFlags`.
- Undo общий: единица undo всегда касается одного слоя (активного), биты NEW/SHADOW глобальны.
- План прохода — один на все слои, ≤ 32 нот → один плеер, один `start()` на проход, общий баланс нот.
- **Отклонение от «отдельной памяти слоя»:** ёмкость 32 общая на оба слоя. Отдельные массивы 2 × 32 дадут
  план до 64 нот → второй плеер (+408 Б) или обрезку. Если владелец настаивает на гарантированных 32 на
  слой — это +128 Б (второй массив) +~408 Б (второй плеер) в фазе 3, интерфейс слоя от этого не меняется
  (`LoopLayerView` скрывает раскладку).

### 3.5 Решение 2026-11-04: BARS 8 и пул 64

- **BARS 1 → 2 → 4 → 8 → 1** (`setBars`/`cycleBars`), проход до 128 шагов (`kMaxLoopSteps = 128`).
- **Событие осталось 4 Б.** 32 бита: онсет 7 + длина 7 + высота 7 + velocity 7 + слой 2 + NEW + SHADOW.
  Байты: `onsetLayer` = онсет (0..6) + слой бит 0 (7); `lengthLayer` = длина (0..6) + слой бит 1 (7);
  `noteFlag`/`velFlag` — как были (NEW в бите 7 высоты, SHADOW в бите 7 velocity). Длина 0 = нота
  держится; 127 = «до конца прохода» (насыщение). Неточность одна: нота с онсета 0 длиной ровно 127 шагов
  в 8-тактовом проходе звучит 128. Вариант 5 Б отвергнут: +64 Б только на пул ради этого одного шага.
- **Пул 64** на оба слоя. Индекс пула в таблице открытых нот — 6 бит (0..63), таблица осталась 6 записей.
- **План прохода ≤ 32 ноты** (`ResponsePlan::kCapacity` и плеер партнёра не менялись). Проход с большим
  числом нот играется несколькими планами подряд: `buildPlan(..., carry, &nextStep)` обрывает план на
  самом позднем шаге, где ещё ≤ 32 нот и через который не звучит ни одна нота; `Looper::service` стартует
  следующий план на этом шаге. Если такого шага нет (бурдон через весь проход), граница — последний
  влезающий шаг: звучащие через неё ноты получают NoteOff на границе и NoteOn снова в начале следующего
  плана (ретригер, баланс сохраняется). Ноты ≤ 32 — ровно прежний один план на проход.
- Старт следующего плана опаздывает на один проход главного цикла — как старт прохода на даунбите.
- **Экран:** при BARS 8 полоса (~150 px, ~1.2 px на шаг) рисует только отметки тактов, такт 5 — во всю
  высоту; отметки долей — пока доля ≥ 6 px. Счётчик `N/64`, предупреждение с 60.
- **DRAM:** `sizeof(Looper)` 200 → 336 на цели (+128 пул, +1 `nextSegment_`, 7 — выравнивание
  `LoopClock`); сборка `build_cardputer_dynbuffers.sh`: 186004 → 186132 (+128 Б, потолок 191488).

## 5. Реальное время

- Всё в главном цикле: NoteOn/Off приходят из `PerformanceKeyboard` в главном цикле [код]
  `performance_input_observer.h:9-11`; `serviceLooper()` — раз за проход цикла. Ни аудиопотока, ни
  диспетчера USB, ни блокировок.
- Без аллокаций, без ФС, без `String`/`std::vector`; фиксированные массивы; уплотнение пула O(32).
- Порядок в `serviceLooper()`: `player.service(now)` → закрыть проход (если позиция ≥ конца) → commit
  open-нот → план → `player.start(plan, downbeat, …)` → `player.service(now)`. Хвостовой NoteOff прошлого
  прохода уходит раньше NoteOn нового (как в PHASE7).
- Лог `[LP]` (одна строка на переход и на проход: `state= pass= notes= new= drop= late=us stale=`), без
  строк длиннее 96 Б на стеке.
