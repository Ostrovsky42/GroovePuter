## D. Retained region — unobtainable from this artifact

Verified against the R0 tree at `c1f71c2b`:

- `loop-enter` / `loop-exit`: not present anywhere.
- Stage writes with values 110/112/114/116/118/120/122/124/126: none.
- `src/platform/` has `retained_boot_stage.h` and `cardputer_wdt_diagnostics.*` only; there is
  no `cardputer_runtime_diagnostics` module.
- `git diff --stat c1f71c2b HEAD` shows HEAD ahead by exactly that module (438 insertions).

§6-D specifies markers 110–126 as D0's localization evidence. They do not exist in the frozen
binary. What R0 retains is `retained_boot_stage`, which stops at stage 100 — the known
zero-discrimination dead end. Even a flawless D0 on this ELF cannot produce group D.

## This run weakens one earlier claim

[RUNTIME_PANIC_LOCALIZED_2026-09-06.md](RUNTIME_PANIC_LOCALIZED_2026-09-06.md) reads the
`CARD_NONE` failure as "the mount needs one contiguous block of ~29.5 KB, and fails when
fragmentation leaves nothing that large."

Here the **first** mount attempt failed with `largest=31732`, which is larger than the 29512 B
request seen previously. A single-contiguous-block model does not explain that failure. Either
the SD path needs more than one large block, or a larger one than 29512 B, or the first failure
has a different cause entirely.

The `~29.5 KB contiguous` reading is therefore **downgraded from "strongly supported" to
"insufficient"**, and per the protocol's §8 rule `SD DIRECT CAUSALITY` stays
`CORRELATED ONLY`.

## Single recommended next diagnostic step

Re-freeze the baseline on a commit that contains `cardputer_runtime_diagnostics`, and repeat
the run with the SD card actually mounted — that is the only branch observed to panic, and
that module is the only instrument that has so far named the faulting task, phase and failing
allocation. Repeating D0 on the current frozen ELF is not recommended.
