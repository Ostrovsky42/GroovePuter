## 1. Contract

1. **The musician explicitly chooses** what may be replaced. Preview text: *"The material stays until the next generation, then may be replaced. Restoring the previous content through Undo is not guaranteed."*
   Marking never starts a generation.
2. **Protection beats the mark.** Song/Phrase-Bank references, CURRENT, working material, queued NEXT and the live Undo receipt exclude reuse. A mark alone therefore does **not** unblock GROW in the
   PML-A scenario: slots 4-11 stay protected (and slots 0-3 give only a 4B run). The Undo receipt is never discarded to make room.
3. **"Generated by the generator" and "allowed to be replaced" are different facts.** Provenance explains and proposes candidates; it never grants overwrite. **A manual edit revokes the permission.**
   `unknown/manual` forbids automatic freeing but **not** the musician's explicit choice: slots 0-3 may be offered for manual selection, never declared trash by the system.
4. **Two results are shown:** the contiguous run available now and the run that becomes available after the permitted reuse, for the selected TAKE/GROW: "4B possible, 8B impossible" with the reason.

## 3. Answers to the five questions

1. **Persistence and cold boot.** Content and descriptors persist (T1). A permission would need a durable home: the page file is binary with version-appended sections (`kind`, `id`, `storageGeneration`);
   a durable mark would be a **format v7** append (plus migration and alignment with the dual-generation publication record). Generated material is not on disk until a page save, so a durable mark could outlive or precede its content.
   **Recommendation for the first implementation: session-only marks** (RAM, dropped on boot and scene load). That fails closed: less space is freed after a boot, nothing is ever lost. Cost to size explicitly:
   a mark is (slot, content token) = about 16 B per slot, 256 B for a page; the current DRAM headroom is 1696 B of the 191488 B budget, so the mark list must be bounded and budgeted.
2. **Revocation on edit.** Do not hook every edit path: store the content token at marking time and **compare at reuse** (T2). Any change, from any path, revokes; identical rewrites do not. A cold-booted slot keeps its token.
3. **Failure during replacement.** PREPARE is pure and refuses without mutating (T3). The replacement must reclaim and write inside the same guarded commit as the generation, after the token check, so there is no state
   "reclaimed but not generated". If commit fails nothing was reclaimed. **[OPEN]** a save failure after commit: generation today publishes RAM only, so durability is a separate step; a failed later save leaves RAM
   and disk different, exactly as for any generated phrase now.
4. **Pattern and Melody through the existing Material owner.** The owner for durable replacement is `PatternPagingService::commitPageCandidate` (dual-generation, read-back verified, NVS publication record) used by ACCEPT.
   Pattern replacement is one descriptor/pattern candidate; **Melody replacement has two steps** (payload file on SD through `MelodyPromotion::commitMelodyCandidate`, then a Melody descriptor commit with rollback of the payload
   on failure). **Recommendation: Melody slots are out of the first slice** (T5: a different owner, irreversible payload on SD). Marking applies to Pattern slots only.
   Note: phrase generation does not use `commitPageCandidate`; it writes RAM and persists at page save. Reuse at generation time therefore inherits that.
5. **What Undo can undo.** Only the generation itself: rows come back and the slots the generation created are cleared (T4). The overwritten previous content is **not** restored, by design of the contract. The receipt is
   1536 B (Song copy 1032 B); one slot's content is 1416 B, so restoring overwritten content would need a separate mechanism (snapshot file or a larger bounded region). Not part of this slice.

## 4. Not in this slice

Freeing protected slots (cycle rows 4-11), extending Undo, Melody slots, automatic marking, a material browser, moving slots.

## 5. Candidate next slice (PML-C), for the owner to approve

Session-only mark list for Pattern slots (bounded, budgeted), `mark/unmark` actions with the preview of section 1, token check inside the generation commit, and the two-run preview. Acceptance: T1-T5 behaviour
unchanged; a marked slot is reused only when unprotected and unedited; an edited marked slot is skipped without error; a refusal changes nothing; all gates green; DRAM delta reported.
