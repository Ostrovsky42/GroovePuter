# Hardware protocol — BLOCKED, not executed

Purpose: obtain runtime baseline, not approve optimization. All measurements must identify firmware, board and instrument. Do not flash without the operator's approval. Back up SD contents and save a known-good firmware plus the exact restore/upload procedure before starting. Record board revision, chip revision, flash/PSRAM detection, power source, SD card, connected MIDI device/firmware, USB role and host, temperature if relevant, source SHA, dirty state, FQBN, SDK/toolchain versions, binary SHA-256 and serial baud. Verify `PSRAM=disabled` in build separately from physical chip capacity. Use each supported profile, separately, with the same fixtures; CDC logging and MIDI-only differ, so choose a working external capture/serial path and report missing observability rather than assume CDC exists.

1. Prepare clean checkout and build the corresponding **product** image using BUILD_MANIFEST.md; retain ELF/MAP/log/hash. Build the corresponding **runtime** diagnostic with the repository's `scripts/build_cardputer_memory_baseline.sh normal runtime --warnings all` or `midi-only runtime --warnings all`; set `MEMORY_BASELINE_FS1=1` and a distinct `BUILD_PATH` for FS1B. Preserve product and runtime image hashes and section differences: diagnostic overhead is not product free memory. The existing temporary instrumentation must be reviewed against the actual source and profile first. Do not call its upload command until operator approves and recovery is ready.
2. Connect serial monitor at configured baud and save raw, timestamped output. Perform at least five independent cold boots per profile. Record init success and existing boot heap checkpoints; calculate startup failures. Warm display/pages, SD, audio, MIDI and lazy SMF, then capture at least 10 seconds of idle. Existing `[MEM-BASE]`/`[MEM-STACK]` definitions are in `docs/stages/CARDPUTER_MEMORY_RUNTIME_TELEMETRY.md`; verify their emission and units with the pinned SDK. Do not trust acceptance overlay stack numbers until the unit discrepancy in LIFETIME_MATRIX is resolved.
3. Run each workload at least three independent times, cold-booted when comparing boot minima. Mark start/end and retain fixture, seed, tempo, routing, timing resolution, raw logs and timestamps. W0 boot; W1 idle/playback internal, MIDI and INT+MIDI; W2 maximum supported notes/events, tempo, transport, TIE and Note Off; W3 repeated fixed-seed genre/DEVELOP while switching UI and playing; W4 FORM/song/scene/macro transitions; W5 save/load, backup recovery, cancellation and SD failure; W6 MIDI connect/disconnect/reconnect with active notes and panic; W7 combined supported peak; W8 at least 60 minutes for finalists. Record each unsupported/unobservable case as BLOCKED with reason; do not simulate a successful physical result.

Never add overlapping capability pools. Existing telemetry may not cover all requested fields or allocation attribution: mark those fields BLOCKED until a separately reviewed MAO-1 diagnostic image provides them. Record per-task configured stack, task presence and raw high-water bytes; run error and deep UI/storage paths. Capture allocation failures and recovery.

Heap low-watermarks may combine per-region lows at different times; distinguish them from sampled scenario minima. Compare same quiescent state after warm-up to assess growth. Do not set a candidate timing threshold until baseline data are examined; provisional memory targets in README are not measured acceptance results.

Pass/fail for an experiment must preserve all existing product and CI gates, feature behavior, MIDI/audio correctness, no new crashes/underruns, and document minimum internal heap, largest suitable DMA block, stack margin and baseline variability.
