# Cardputer Runtime Panic Localization Implementation Plan

> **For agentic workers:** Use superpowers:executing-plans to execute this plan task-by-task in one session. Steps use checkbox syntax. Hardware and the serial port have one operator; do not start parallel flashing or capture sessions.

**Goal:** Установить непосредственный механизм panic после успешного монтирования SD, исправить его и проверить совместную работу SD, UI, аудио и MIDI на точно идентифицированной прошивке.

**Architecture:** Сначала добавить ограниченный диагностический прибор: первую ошибку аллокатора, независимые отметки задач и снимки памяти. После различающего аппаратного наблюдения выбрать один минимальный фикс. Статический DRAM-гейт и тесты музыкальных контрактов остаются отдельными проверками и не заменяют аппаратную проверку.

**Tech Stack:** Cardputer ADV / ESP32-S3 без PSRAM; Arduino m5stack:esp32 3.2.2, ESP-IDF 5.4; FreeRTOS; C++17; Python 3; существующие Arduino build scripts и host tests.

**Spec:** Запрос пользователя от 2026-09-06 и его разбор недостаточной различающей способности измерений; исходные свидетельства: `docs/audits/SD_PANIC_LOOP_WITHOUT_AUTOSAVE_2026-09-06.md`, `docs/audits/CARDPUTER_RECOVERY_REVIEW_2026-09-05.md`, `logs/serial-180s-20260906-003326.log`. Выводы документов проверять по сырому логу и исходнику, с учётом поправок ниже.

## Global Constraints

- Не менять музыкальное поведение, размеры очередей, стеки или порядок старта по догадке.
- Не повышать потолок `191488` ради зелёного результата. Это временная политика статической памяти, не доказанный безопасный предел устройства.
- Не добавлять выделения памяти, Serial, файловый I/O или ожидание mutex в callback отказа аллокатора и в аудиотракт.
- Инструментация только в отдельной диагностической сборке; production-вариант должен компилироваться без её хранения и вызовов.
- Один владелец устройства и один читатель serial. Одновременные мониторы могут делить поток между файлами.
- Не форматировать карту и не удалять сцены. Контроль без autosave уже выполнен; не повторять его без новой причины.
- На текущем этапе создаётся план. Прошивка и запуск аппаратных экспериментов в него не входят автоматически. При исполнении получить явное разрешение на загрузку конкретного проверенного образа, как требует `.agent/skills/embedded-runtime-debugging/SKILL.md`.
- Не использовать rebase. Не трогать пользовательские `platform_sdl/grooveputer_scene.auto.json` и `platform_sdl/patterns/`.
- Не заставлять неизвестный аппаратный отказ проходить искусственный RED тест фичи. Host-тесты сначала проверяют достоверность прибора; тест исправления появляется после локализации механизма.

## Что уже известно и чего это не доказывает

В указанном 180-секундном логе есть последовательность:

```text
перед SPI/SD:       freeInt=43836 largest=31732
после mount OK:     freeInt=13692 largest=7668
после SMF init:     freeInt=4168  largest=2292
после setup:       freeInt=680   largest=628
следующая загрузка: Reset Reason: 4; Previous stage retained: 100
```

Интервал SPI/SD расходует 30144 байта. Это уже происходящий при старте расход, а не доказанная утечка в loop. Следует разделить SPI, SD/FAT/VFS и callback регистрации сэмплов. Низкая куча не доказывает причинность OOM. `stage=100` означает последнюю записанную веху setup, а не место или задачу исключения.

Утверждение «21 загрузка» в старом аудите отозвано пользователем: это было количество текстовых совпадений. Для оценки воспроизведения считать целые эпизоды по идентификаторам загрузок. `dispatchedControl` доказывает извлечение события диспетчером, но само по себе не доказывает звук внешнего приёмника.

## Task 1: Зафиксировать воспроизводимый случай и происхождение свидетельств

**Files:** читать три источника из Spec и `scripts/serial_monitor.py`; создать `docs/audits/CARDPUTER_RUNTIME_PANIC_2026-09-06.md`.

- [ ] Записать текущий commit, dirty state, ELF SHA-256, FQBN и версии реально использованных библиотек. HEAD не считать идентификатором уже загруженной прошивки.
- [ ] Описать подключение: USB-хост, MIDI-потребитель, DIN-приёмник, карта, активная страница и действия перед отказом. Не интерпретировать «MIDI не звучит» без указания тракта.
- [ ] Проверить, что другие сессии не прошивают прибор; сохранить существующий лог перед переключением монитора.
- [ ] Из сырого лога выписать один полный эпизод: mount → SMF → UI → setup-complete → последующая причина сброса. Для каждого числа указать файл, строки, смысл поля и измеренный интервал.
- [ ] Завести таблицу гипотез ниже. Отделить наблюдение, интерпретацию и условие опровержения.

| Гипотеза | Различающая улика | Ограничение |
|---|---|---|
| Выделение не помещается в оставшуюся кучу | Первая ошибка аллокатора: размер, capabilities, задача; снимок памяти непосредственно перед ней | Ошибка выделения может быть обработана; одной записи недостаточно для приписывания причины panic |
| Фрагментация | Неудачное выделение при достаточном суммарном объёме и недостаточном крупнейшем блоке для тех же capabilities | Суммарный INTERNAL/8BIT не описывает все виды запросов |
| Повреждение кучи | Переход integrity OK → FAIL в ограниченном интервале | Сам повреждающий код мог выполниться раньше обнаружения |
| Переполнение стека | Stack canary/watchpoint либо соответствующий panic/backtrace, низкий high-water mark нужной задачи | Большой остаток loop не исключает отказ другой задачи |
| Другой assert/exception | Сохранённый panic reason и адреса, разобранные точным ELF | Отсутствие callback аллокатора не доказывает достаточность памяти |

**Выход:** один воспроизводимый случай, без необходимости снова выполнять длинный набор ручных действий.

## Task 2: Построить прибор для первой ошибки и состояния задач

**Files:** создать `src/platform/cardputer_runtime_diagnostics.h/.cpp`, `tests/test_cardputer_runtime_diagnostics.cpp`; подключить из `GroovePuter.ino`, `src/platform/cardputer_smf_player.cpp`, `src/platform/cardputer_usb_midi_transport.cpp`, `src/platform/cardputer_sd.cpp`; включить через `scripts/build_cardputer_recovery_diagnostics.sh`. Использовать существующий `retained_boot_stage.h` как образец валидации RTC, не превращать его в общий счётчик для всех задач.

**Интерфейс диагностического адаптера:**

```cpp
namespace CardputerRuntimeDiagnostics {
enum class Task : uint8_t { Loop, Audio, Smf, Midi, Other };
enum class Phase : uint8_t {
  Enter, Keyboard, Control, Ui, AudioRender, AudioWrite,
  SmfService, MidiService, BeforeSpi, AfterSpi, BeforeSd, AfterSd,
  BeforeSdReadyHook, AfterSdReadyHook, Idle
};
void begin();                       // прочитать предыдущую запись, начать текущую
void registerCurrentTask(Task task);
void checkpoint(Task task, Phase phase);  // только запись фиксированных полей
void sampleFromControlTask();       // память/стеки, вне callback и аудио
void reportFromControlTask();       // ограниченный вывод уже снятых данных
}
```

- [ ] Выделить фиксированную запись RTC без конструктора: версия формата, идентификатор образа/загрузки, отдельные слоты задач, последовательность публикации, первая ошибка выделения, последний снимок памяти. Валидировать завершённость записи; повреждённую или чужую запись не декодировать как достоверную.
- [ ] Написать host-тесты записи: незавершённая публикация отвергается; первый отказ сохраняется при последующих; слот Audio не затирает Loop; после cold boot старые данные игнорируются; запись от другого образа явно помечается; повторный вывод не считается новой загрузкой.
- [ ] Подключить установленный API, проверить результат регистрации:

```cpp
// Сигнатура из установленного esp_heap_caps.h:
void onAllocationFailed(size_t size, uint32_t caps, const char* function_name);
// heap_caps_register_failed_alloc_callback(&onAllocationFailed) == ESP_OK
```

Callback хранит размер, capabilities, core, известный Task tag и идентификатор функции в заранее выделенной записи. Не вычислять heap statistics, не форматировать строки, не вызывать Serial и не ждать блокировок. Уточнить контекст callback в установленном SDK до выбора способа публикации. Для конкурентных вызовов использовать независимые слоты по core и атомарную публикацию 32-битного состояния; проверить, что реализация lock-free на целевой платформе. `function_name` — имя функции аллокатора, а не обещанный call site. Не подменять backtrace адресом возврата самого hook.

- [ ] Зарегистрировать владельцев внутри стартовых функций Loop/Audio/SMF/MIDI. Расставить вход/выход существенных участков; чтение RTC после перезапуска не должно зависеть от валидности старого TaskHandle.
- [ ] Снимать free/largest INTERNAL|8BIT на границах SPI, SD, ready-hook и SMF/UI-инициализации; в runtime — не чаще раза в секунду из control task. Снимать high-water mark зарегистрированных задач в байтах. Чтение watermarks проверяет только реально существующие задачи.
- [ ] Проверку `heap_caps_check_integrity_all(false)` включить отдельным диагностическим режимом: на границах подозрительного участка. Измерить длительность; сравнить с режимом без проверки, чтобы не скрыть отказ изменением тайминга.
- [ ] Проверить host-тестами recorder и адаптер с заглушками отказа/конкурирующих публикаций. Через ELF/map подтвердить отсутствие диагностического хранения в production и измерить добавленную память в диагностике. Задать прибору бюджет до реализации: RTC ≤512 Б, дополнительная статическая DRAM ≤256 Б, нулевой heap; это бюджет прибора, не критерий безопасности продукта.
- [ ] Выполнить сборку отдельного образа и статический gate. Не загружать старый бинарник после неуспешной сборки. Записать точный ELF SHA.

**Выход:** прибор сообщает конкретный отказ или ограничивает интервал, не создавая новые выделения памяти в месте отказа.

## Task 3: Один короткий аппаратный прогон с заранее заданным решением

**Files:** сырой новый `logs/serial-...log`, результаты в аудите Task 1.

- [ ] После разрешения на проверенный диагностический образ: один монитор, прежняя карта и минимальный сценарий из Task 1. MIDI-потребитель на ПК фиксирован в одном состоянии.
- [ ] Остановить сбор после первого полного эпизода с пригодной записью; первоначальное окно — до 30 секунд, без бесконечного перепрошивания. Если сбоя нет, зафиксировать отсутствие воспроизведения и влияние диагностики, не объявлять исправление.
- [ ] Если найден allocation failure: сопоставить размер/caps/task с последним снимком и исходниками соответствующего пути. Проверить, обрабатывает ли вызывающий код отказ или завершает процесс/assert. Когда snapshot не покрывает нужные capabilities, сузить измерение именно под этот запрос.
- [ ] Если найдена порча кучи: сузить границы проверки вокруг первого перехода integrity, не уменьшать буферы как предполагаемое лечение.
- [ ] Если доказательства стека: локализовать задачу и её кадры. Не увеличивать все стеки, отнимая оставшуюся кучу.
- [ ] Если снова получены лишь panic и последние checkpoints: прекратить повторы. Проверить конфигурацию panic/coredump установленного SDK и сохранность вывода. Выбрать один доступный путь получения backtrace/core dump; при необходимости отдельной конфигурации SDK оформить её как диагностический эксперимент с измеренной ценой. UART для panic нельзя занимать без проверки конфликтов с I2S и MIDI-пинами.

**Условие перехода к исправлению:** известен механизм и участок кода, а наблюдение отличает его хотя бы от ближайшей конкурирующей гипотезы. Последний checkpoint сам по себе не является адресом падения.

**Выход:** таблица «владелец → байты → время жизни → максимальное совместное использование». Если Task 3 указывает другой механизм, этот бюджет остаётся отдельной проблемой и не подменяет его исправление.

## Task 6: Проверка результата и условия закрытия

- [ ] Повторить исходный короткий сценарий на исправленном диагностическом образе; сравнить с предсказанием Task 5.
- [ ] После успешного короткого прогона проверить production-образ без диагностики: mount, просмотр MIDI-файлов, SMF play/stop, внутренний звук и live MIDI на PERFORM, переходы страниц и загрузку/сохранение тестовой сцены.
- [ ] Проверить USB с открытым и закрытым MIDI-потребителем; оценивать звук на выбранном приёмнике отдельно от счётчиков dispatch/write.
- [ ] Выполнить три последовательных корректных старта с SD и один старт без SD. Затем 10 минут рабочего сценария с SD и повторением операций, без дополнительных перепрошивок. Это ограниченная проверка восстановления, не обещание отсутствия всех будущих сбоев.
- [ ] Установить runtime-резерв из максимального необходимого запроса, capabilities и одновременных ресурсов Task 4, с обоснованным запасом. До этого не вводить произвольный «безопасный минимум» в байтах. Проверить free и largest под соответствующие требования.
- [ ] Закрыть только при известной причине, ожидаемом эффекте исправления, отсутствии panic/необработанных allocation failures/нарушения heap integrity, выполнении runtime-резерва и успешных пользовательских сценариях. Старый отказ mount при необходимости оставить отдельным открытым пунктом.

Каждое заключение в аудите содержит: build identity, boot identity, файл и строки доказательства, определение счётчика, наблюдение, вывод и оставшееся ограничение. Исправленные неверные выводы явно помечать как отозванные, чтобы они не пережили компактификацию как факты.

## Порядок исполнения

Tasks 1 → 2 → 3. После локализации Task 4 объясняет ресурсный бюджет, Task 5 исправляет доказанный механизм, Task 6 проверяет результат. Если Task 3 не различил гипотезы, меняется прибор; дополнительные одинаковые прогоны не засчитываются как прогресс. Новые изменения фич до завершения этого пути не добавляются.
