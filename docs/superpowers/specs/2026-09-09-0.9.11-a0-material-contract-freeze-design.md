# 0.9.11-A0 — Material Contract Freeze

## Status

Architecture design only. No production behavior changes in this checkpoint.

Authoritative architecture line:

```text
architecture/20260909-0.9.11
```

This design replaces the earlier implicit assumption that one large `MaterialId`
or one central material service should become the root of all 0.9.11 work.
Instead, 0.9.11 freezes a small set of bounded value contracts so persistence,
Song, Phrase Bank, GF2, UI and runtime can evolve in parallel without sharing
implementation ownership.

---

## 1. Problem

The 0.9.10 integration established several strong local components:

- one runtime active-note lifetime owner;
- M3 explicit ACTIVE authority;
- M4 NEXT prepare/activate boundary;
- bounded runtime buffers;
- no filesystem work in the audio path;
- explicit MelodyStore file ABI with CRC;
- GF2 multi-bar Phrase semantics;
- Phrase Bank direction where EDIT state does not become PLAY authority.

The remaining architectural failures are mostly cross-boundary failures:

- page-local slots can alias the same Melody sidecar;
- runtime `currentPhrase_` can disagree with persisted Material kind;
- page changes can leave stale audible Melody state;
- unavailable/not-resident can collapse to Pattern;
- Song still reasons in Pattern-centric references;
- project copy/save-as can move descriptors without Melody payloads;
- UI pages can coordinate domain/runtime/persistence transactions directly.

The common cause is not a missing framework. It is the absence of a small,
shared contract vocabulary between independent owners.

---

## 2. Design principle

Parallel development is a design constraint.

A subsystem boundary is considered healthy when another workstream can depend on
its contract without depending on its implementation, storage layout, UI state,
or runtime internals.

The target shape is:

```text
                         GF2
                   musical candidate
                         |
                         v
UI intent ---> application operation ---> persistence
                         |
                         v
                  prepared runtime
                         |
                         v
                    ACTIVE / NEXT
                         |
                         v
                      playback

Phrase Bank: EDIT target only
Song: arrangement occurrences only
```

No side owner may directly become audible authority.

---

## 3. Frozen contract vocabulary

### 3.1 `MaterialKind`

Canonical musical representation kind:

```text
Pattern
Melody
```

`Phrase` is not a Material kind.

GF2 Phrase remains a real multi-bar structural concept and is not renamed by
this checkpoint.

Runtime names such as `currentPhrase_` are legacy implementation vocabulary and
must not define the domain model going forward.

### 3.2 `MaterialAddress`

A project-relative musical address:

```text
MaterialAddress
    voice
    globalSlot
```

Properties:

- does not contain project name/path;
- does not contain page, bank or resident/local slot;
- does not contain Material kind;
- is valid for Song, edit targeting and control-side resolution;
- page/bank/local-slot are projections of `globalSlot`, never identity owners.

This is the primary cross-workstream reference contract.

### 3.3 `PersistentMaterialId`

Persistence-only identity concept:

```text
PersistentMaterialId
    ProjectNamespace
    MaterialAddress
```

Only persistence needs project namespace.

Audio, Song, Phrase Bank and GF2 must not depend on project path or SD naming.

The physical GPML path is an implementation detail derived from this identity,
not the identity itself.

### 3.4 `MaterialResolutionStatus`

Control-side resolution must be explicit.

Minimum semantic states:

```text
Resolved
NotResident
MissingPayload
CorruptPayload
InvalidAddress
InvalidKind
```

Additional bounded failure values may be added only if they represent a distinct
recovery decision.

Forbidden fallback:

```text
unknown / unavailable / not resident -> Pattern
```

Only `Resolved(kind = Pattern)` means Pattern.

### 3.5 `MaterialResolution`

Conceptual result:

```text
MaterialResolution
    MaterialAddress address
    MaterialResolutionStatus status
    MaterialKind kind        // meaningful only when Resolved
    bounded prepared source / handle as appropriate to caller
```

A resolution result is control-side state. Audio receives only a fully prepared,
fully resolved bounded runtime representation through the existing M3/M4 path.

### 3.6 `MaterialOperationReceipt`

Application operations return a small musician-visible outcome instead of
forcing UI code to infer transaction state.

Minimum semantic outcomes:

```text
AppliedNow
QueuedNextBoundary
Rejected
Unavailable
Failed
```

Storage- or implementation-specific errors may exist internally but should map to
stable operation-level outcomes before reaching UI.

## 4. Ownership boundaries

### 4.1 GF2

Owns:

- musical idea selection;
- genre laws;
- structural phrase development;
- harmonic clock;
- phrase evolution;
- bounded generated material candidates.

Does not own:

- project identity;
- SD path;
- active material selection;
- paging;
- Song arrangement references;
- UI navigation.

GF2 may evolve in parallel with Material persistence work.

### 4.2 Phrase Bank

Owns EDIT target only.

Target invariant:

```text
EditTarget != PlayTarget
```

Existing direction where `PhraseBankState` stores only per-voice editing slot and
`MiniAcid::activeMaterial()` remains audible authority is accepted.

Phrase Bank must use `MaterialAddress`/slot semantics only as needed for edit
selection. It may never acquire ACTIVE/NEXT authority.

### 4.3 Song

Owns arrangement occurrence semantics:

```text
EMPTY
REST
MATERIAL(globalSlot)
```

A Song lane/track supplies voice identity. Therefore a material occurrence plus
lane resolves to:

```text
MaterialAddress { voice, globalSlot }
```

The existing bounded two-byte `SongCell` direction is accepted, but Pattern-only
vocabulary such as `patternRef()` is transitional and must not become the final
contract.

Song does not decide whether a referenced Material is Pattern or Melody.

### 4.4 Persistence

Owns:

- `ProjectNamespace`;
- `PersistentMaterialId`;
- page descriptor persistence;
- Melody payload persistence;
- GPML path derivation;
- CRC/readback validation;
- save-as/copy/rename/delete material lifecycle;
- orphan policy;
- power-loss transaction semantics.

Persistence does not publish directly to audio.

### 4.5 Application operations

Own musician-level transactions that cross boundaries.

Examples:

```text
MakeMelody
SelectMaterial
SwitchPage
ApplyGenreIntent
ApplySongOccurrence
```

These are concrete operations, not a generic command bus.

Typical flow:

```text
PREPARE
-> VALIDATE
-> PERSIST where required
-> RESOLVE
-> PREPARE RUNTIME
-> COMMIT / STAGE NEXT
-> RECEIPT
```

UI sends intent and renders receipt. UI pages do not coordinate storage/runtime
transactions directly.

### 4.6 Runtime M3/M4

Own:

- fully resolved ACTIVE material;
- fully prepared NEXT material;
- boundary activation;
- playback publication.

Keep:

- current bounded buffer strategy;
- current fixed-lifetime allocations where already justified;
- no filesystem in audio;
- one runtime active-note lifetime owner;
- hard barriers only on ownership transfer/source change.

Do not add project, page, filesystem or Song semantics to audio.

## 5. Material identity projections

The following are projections only:

```text
globalSlot -> page
globalSlot -> bank
globalSlot -> localSlot
(page, bank, localSlot) -> globalSlot
```

No persistent path may be based solely on `localSlot`.

Required identity invariant:

```text
same project + same voice + different globalSlot
    => different persistent material identity
```

Required cross-page regression:

```text
page 0 / voice A / local slot 5
page 1 / voice A / local slot 5
    => two independently addressable Melody payloads
```

The existing A1 RED characterization is the first consumer of this contract, not
the authority that defines the contract.

---

## 6. Paging contract

Page switching is a material-context transition, not merely a Pattern bank swap.

Target control-side sequence:

```text
request page
-> load / prepare page
-> validate descriptors
-> resolve material addresses for voices
-> rebuild Pattern runtime bank
-> prepare Melody runtime buffers where required
-> commit page context
-> publish ACTIVE/NEXT through existing M3/M4
```

Invariant:

> After page transition, no event from a material owned by the previous page may
> remain audible unless that exact material was deliberately resolved as the new
> target.

A note lifetime barrier may terminate old ownership, but bar boundaries remain
non-barriers for valid cross-bar notes within the same material owner.

---

## 7. Promotion contract

`Pattern -> Melody` is one application operation.

The operation must not leave these authorities disagreeing:

```text
Scene descriptor
persistent GPML payload
control-side resolution
ACTIVE / NEXT
UI presentation
```

The existing engine-level `makePhrase()` / `currentPhrase_` path is not a final
domain operation. It may survive only as a bounded converter/helper during
migration.

Final vocabulary:

```text
Material = Pattern | Melody
Phrase   = structural multi-bar arrangement/development concept
Song     = arrangement of material occurrences
```

---

## 8. Durability direction

Default product contract for 0.9.11 design:

> A successful user-visible MAKE MELODY operation is durable and must survive
> reboot without requiring a second hidden Save operation.

Therefore persistence must define a transaction in which success is not reported
until the descriptor/payload pair is recoverable as one canonical material.

Acceptable recovery after power loss:

```text
old valid Pattern
or
new fully valid Melody
```

Forbidden successful end state:

```text
descriptor = Melody
payload = missing/corrupt/unaddressable
```

Exact write/rename ordering belongs to the persistence implementation checkpoint,
not A0.

---

## 9. Parallel branch model

After A0 contract freeze, these lines are intentionally parallel:

```text
A1 Persistence Identity
A2 Canonical Promotion
A3 Paging Resolution
A4 Project Lifecycle / Durability

B1 SongCell Material semantics
B2 Song material resolution

C1 Phrase Bank edit-target integration

G4 Reference Genre / Phrase semantics
```

G4 may proceed independently so long as it does not claim persistence, paging or
runtime authority.

Phrase Bank may proceed independently so long as it remains EDIT-only.

Song may evolve occurrence storage independently, but final resolution must use
`MaterialAddress` rather than Pattern-specific interpretation.

---

## 10. Integration checkpoint

The parallel lines converge at:

```text
0.9.11-I0 MATERIAL CAUSALITY
```

Required end-to-end proof:

```text
musician intent
-> one MaterialAddress
-> one persistent truth
-> one resolved truth
-> one ACTIVE/NEXT truth
-> one audible truth
```

Adversarial scenarios:

1. same local slot on two pages;
2. Melody active, then page switch;
3. empty page initialization after Melody page;
4. Song occurrence references off-page Melody;
5. missing/corrupt Melody payload;
6. power loss during promotion transaction;
7. NEXT Melody prepared, then page/project context changes before boundary;
8. Save As with promoted Melodies;
9. project deletion and orphan cleanup;
10. EDIT target changes while PLAY authority remains unchanged.

---

## 11. Error handling principles

- fail closed before audio publication;
- never silently coerce unresolved state to Pattern;
- never perform storage recovery inside audio;
- preserve old valid state when a new operation cannot be completed atomically;
- distinguish user-visible operation outcome from low-level storage error;
- one failed voice/material preparation must not partially publish mixed identity.

---

## 12. Memory constraints

A0 introduces contracts, not new resident systems.

Requirements for implementation checkpoints:

- prefer POD/trivially-copyable value types;
- no unbounded containers in runtime authority;
- no new per-event heap ownership;
- no generic message bus;
- static/fixed buffers remain acceptable where bounded and measured;
- every production checkpoint reports fixed DRAM delta and relevant dynamic
  allocation changes;
- preserve M4 fixed-lifetime NEXT buffer strategy unless evidence disproves it.

`MaterialAddress` and Song occurrence types should remain compact enough for
embedded storage and static assertions should enforce that property.

---

## 13. Testing architecture

A0 contract tests should be compile/static/characterization oriented.

Downstream checkpoints use RED -> GREEN evidence:

- A1: cross-page persistent identity;
- A2: one canonical Pattern -> Melody authority;
- A3: stale old-page Melody cannot remain audible;
- A4: Save As / reboot / power-loss recovery;
- B1/B2: Song occurrence resolves Material, not Pattern implementation;
- C1: EDIT selection cannot alter PLAY authority;
- I0: complete musician-intent-to-audio causality.

Every implementation GREEN candidate must use one exact SHA for relevant host
regressions, Cardputer ADV build and memory gate.

---

## 14. Non-goals

A0 does not:

- implement MaterialId/persistence changes;
- rename all legacy Phrase symbols;
- redesign GF2;
- split `Scene` for aesthetics;
- introduce repository/service/command-bus frameworks;
- redesign audio scheduling;
- change bar-boundary lifetime semantics;
- retune genre or FEEL behavior;
- merge parallel feature branches mechanically.

## 16. Freeze criteria

A0 is frozen when the team agrees on all of the following:

1. `MaterialAddress = voice + globalSlot` is the cross-workstream reference.
2. project namespace belongs only to persistence identity.
3. Pattern/Melody are Material representations; Phrase is not a Material kind.
4. Song stores occurrences, not playback authority.
5. Phrase Bank stores EDIT target, not PLAY authority.
6. unresolved material is explicit and never silently Pattern.
7. application operations own cross-boundary musician transactions.
8. M3/M4 remain the runtime publication boundary.
9. persistence owns descriptor/payload atomicity and project lifecycle.
10. parallel branches converge through contracts, not shared implementation
   ownership.

Once these are frozen, implementation planning may proceed without reopening the
high-level ownership model unless a RED test disproves one of the assumptions.
