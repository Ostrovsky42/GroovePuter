## Scope

This checkpoint corrects one architecture contract before any A1/A2 production port:

> `MaterialAddress` is a location. It is not material identity.

The checkpoint is RED-only. It changes no production owner, page-file ABI, scene persistence, promotion behavior, audio path, Pattern/Phrase runtime, G4 behavior, or UI.

A1/A2 are donors, not bases and not merge candidates.

## Why the previous contract is insufficient

The earlier 0.9.11 A0/A1 line froze persistent identity as project namespace plus address. That proves that two different slots do not alias, but it cannot distinguish two different materials that occupy the same slot at different times.

The missing adversarial case is address reuse:

1. material `M` occupies address `A`;
2. a reference captures `M` as `{A, idM}`;
3. `M` is removed/replaced and address `A` is reused by new material `N`;
4. `N` must receive `idN != idM`;
5. resolving the old `{A, idM}` must fail with identity mismatch;
6. resolving `{A, idN}` may resolve `N`.

If step 5 succeeds, address has silently become identity again.

## Required model

These concepts are distinct:

- **MaterialAddress** — where material is currently stored, e.g. synth voice + global slot.
- **MaterialId** — opaque project-scoped logical identity. It survives ordinary mutation and is not derived from address or content.
- **MaterialReference** — a location-bearing reference containing both address and expected MaterialId. Resolution validates both.
- **MaterialVersionToken** — exact-state/content token used for stale-state detection. It is not identity and may change while MaterialId stays constant.

`MaterialId == 0` is reserved as invalid/unassigned. An invalid ID must fail closed. Code must not recover by treating address as identity.

## Identity laws

### I1 — address is not identity

Two incarnations at the same address are not the same material unless their MaterialId is the same by an explicit identity-preserving operation.

### I2 — reuse creates a new identity

Replacing/releasing material and reusing its address for a new material must produce a different non-zero MaterialId.

### I3 — ordinary mutation preserves identity

Editing the same material may change content/version but must preserve MaterialId.

### I4 — reference resolution validates identity

A `MaterialReference` resolves only when both its address is valid and the material currently at that address has the expected non-zero MaterialId.

### I5 — legacy/unassigned state fails closed

A slot with no assigned MaterialId is not allowed to satisfy a persistent MaterialReference merely because the address matches.

### I6 — content hash is not identity

Two byte-identical materials may have different MaterialIds. A content/version hash may not be promoted into MaterialId.

## Persistence ownership constraints discovered on the W0 root

Current W0 stores resident `MaterialKind` in `Scene::materialSlots[2][16]` and persists material kind with each pattern page. `SceneManager` switches resident pages. Therefore a project-wide identity allocator must not be duplicated independently inside each resident page.

The existing project namespace owner is `PatternPagingService::setProjectName/currentProjectName()`. Project page lifecycle already has Save As copy and New/Clear hooks through `copyProjectPages` and `clearProjectPages`.

This identifies the ownership boundary but does **not** freeze the persistence representation in this RED checkpoint.

Before GREEN, compare at least these implementation shapes:

1. **Recommended direction:** opaque 32-bit project-scoped ID + `{address,id}` reference; persist slot IDs with page material and persist allocator state once per project.
2. Address + generation handle: smaller conceptual delta, but still couples identity semantics to location and is therefore weaker.
3. Content hash as identity: rejected by I3/I6.

The GREEN design must account for Save As, New/Clear, legacy pages, transaction rollback, and fixed DRAM before changing the page-file format.

## RED witness

The executable RED is intentionally capability-sensitive:

- if no independent MaterialId/MaterialReference owner exists, it fails with an explicit architecture message rather than compiler noise;
- once the owner exists, the same test must execute the address-reuse witness above and reject old-reference aliasing.

The RED must not be made GREEN by label checks, address inequality, content hashing, or a test-only identity registry.
