# GroovePuter 0.9.11 — M-WORKING design

Date: 2026-09-11
Branch: `feature/20260911-0.9.11-m-working`
Base: `62deb6275c330a8123823542093391c76183ceee`

## Status

Approved architecture choice: **A — reuse the already-paid `currentPhrase_` memory as representation-aware WORKING storage**.

This checkpoint defines the mutable candidate owner for 0.9.11 MATERIAL. It does not implement final persistence replacement, Take history, Scenes, Song, UI-V2, or musician-facing M-UX1.

## Problem

Today Pattern editing mutates canonical Scene state directly and then rebuilds runtime projection from that changed canonical state. Melody/Phrase editing already has a retained runtime buffer (`currentPhrase_[2]`). This prevents a clean application contract in which:

- ACCEPTED is durable and remains unchanged while the user auditions edits;
- WORKING is mutable and session-scoped;
- Undo applies inside WORKING rather than rewinding persistence;
- DISCARD reconstructs WORKING from ACCEPTED;
- Pattern→Melody representation migration is not itself acceptance.

The missing owner is therefore not another musical entity. It is a physical owner for the current mutable candidate.

## Decision

Replace the semantic role of `currentPhrase_[NUM_303_VOICES]` with one **representation-aware WorkingMaterialStorage per synth voice**.

The storage is a union-like owner whose maximum payload remains the existing `RuntimeSynthEventBuffer` footprint:

```text
WorkingMaterialStorage
  kind: derived from authoritative material/source ownership where possible
  payload:
    SynthPattern
    OR
    RuntimeSynthEventBuffer
```

The implementation must not introduce a second full Pattern/Melody copy for the same Working candidate.

The intended memory invariant is:

```cpp
sizeof(WorkingMaterialStorage) <= sizeof(PhraseRuntime::RuntimeSynthEventBuffer)
```

If a representation tag is required, it must fit inside the existing storage budget or be derived from already-authoritative state. A new parallel persistent truth is not acceptable.

## Ownership model

### ACCEPTED

ACCEPTED remains canonical durable truth:

- Pattern: Scene-owned `SynthPattern`;
- Melody: resolver-backed persisted Melody payload and descriptor;
- exact content identity: `MaterialVersionToken`.

Editing must not mutate ACCEPTED.

### WORKING

WORKING is the mutable session candidate for the currently edited material.

For Pattern:

```text
ACCEPTED Scene Pattern A
        │
        ▼
Working Pattern A
        │ edit
        ▼
Working Pattern B
        │ project
        ▼
Pattern runtime hears B

Scene remains A
```

For Melody:

```text
ACCEPTED Melody A
        │ resolve/load
        ▼
Working Melody A
        │ edit
        ▼
Working Melody B
        │
        ▼
Melody runtime hears B

Persisted Melody remains A
```

WORKING is session state. Power loss returns to the last ACCEPTED state unless a later M-ACCEPT checkpoint explicitly adds another durability contract.

## Pattern projection contract

`SynthPattern` remains the lossless Pattern Working representation.

`RuntimePatternEventBuffer` / projected event data must not become the Pattern Working owner because projection is semantic rather than reversible: timing affects onset placement, ties become durations, articulation becomes event flags, and step-level structure is not a lossless inverse mapping.

Runtime projection remains derived sounding state.

## Pattern→Melody migration

Pattern→Melody migration is allowed **inside WORKING** when a user-level musical action requires a richer representation, such as LENGTH growth beyond Pattern capacity.

Example:

```text
ACCEPTED Pattern A
WORKING Pattern B
      │ LENGTH 1 → 4
      ▼
project WORKING Pattern B
      ▼
WORKING Melody B'
      │
      ├─ bar 1 preserves the working idea
      └─ bars 2..4 are filled by an explicit musical operation
```

The canonical descriptor remains Pattern until a later ACCEPT operation succeeds.

Migration must use the current Working Pattern, not stale ACCEPTED Pattern state.

Migration is not SAVE, ACCEPT, NEW TAKE, or persistence.

## Undo / Redo

Undo remains one-level.

Its semantic target changes from canonical Pattern persistence to the current WORKING candidate.

```text
Working B → edit → Working C
Undo  → Working B
Redo  → Working C
```

Undo must not mutate ACCEPTED.

`DISCARD` and `Undo` are intentionally different operations:

- Undo/Redo: last Working mutation pair;
- Discard: reconstruct current Working from ACCEPTED and clear stale Working undo receipt.

No multi-level candidate history is introduced.

## DISCARD

DISCARD reloads the authoritative accepted representation into WORKING and republishes the appropriate runtime form.

Pattern:

1. resolve accepted Pattern coordinate;
2. copy canonical `SynthPattern` into Working Pattern storage;
3. rebuild/project runtime from that Working Pattern;
4. clear stale Working undo receipt.

Melody:

1. resolve accepted Melody;
2. load verified accepted Melody payload;
3. copy into Working Melody storage;
4. publish runtime from Working;
5. clear stale Working undo receipt.

DISCARD performs no persistence write.

## Modified state

Do not add a permanent `workingDirty` flag if the state can be derived.

Preferred truth:

```text
modified = representation differs
        OR exact Working content version differs from ACCEPTED version
```

Use existing exact-version machinery where possible. Pattern/Melody representation difference alone is sufficient to prove modification even if event content sounds equivalent.

If exact Working token calculation is too expensive for continuous UI draw, caching may be considered only if the cache is invalidated by the true mutation owner and does not create a second semantic truth.

## Target switching / navigation

Navigation must not silently ACCEPT or DISCARD a modified Working candidate.

When the requested target changes while current WORKING is modified, the domain layer must expose a conflict/refusal outcome rather than destroy the branch.

M-WORKING does not prescribe the final UI. M-UX1 may later present actions such as ACCEPT / DISCARD / BACK.

Navigation itself remains non-mutating.

## Runtime and ACTIVE/NEXT

Existing ACTIVE/NEXT material causality remains authoritative.

M-WORKING must not create a parallel playback-selection model. It only changes where mutable candidate content is owned before projection/publication.

Failed preparation must leave ACTIVE unchanged. Boundary activation behavior remains unchanged.

## Memory constraints

The base Cardputer checkpoint has effectively no static DRAM slack. Therefore M-WORKING has a hard memory gate:

- no additional full Pattern/Melody Working buffer;
- no new static history ring;
- no page-owned domain buffer;
- no second material-selection state;
- no static footprint increase unless separately justified and proven within the device budget.

Required proof after implementation:

1. compile-time size guard for Working storage;
2. exact-head Cardputer build;
3. DRAM/memory gate against the same release budget;
4. no second full-screen or material buffer introduced indirectly.

## Error handling

The Working owner must distinguish invalid/unavailable accepted material from an editable empty material.

Resolver failures such as NotResident, MissingPayload, CorruptPayload, InvalidAddress, or StorageUnavailable must not be converted into a blank Working candidate.

A failed load/prepare leaves current accepted/runtime truth unchanged.

A failed Pattern→Melody Working conversion leaves the original Working Pattern intact.

## Non-goals

This checkpoint does not solve:

- repeated durable Melody replacement transaction;
- final ACCEPT semantics;
- accepted Take history;
- NEW TAKE / TAKE 03 UI;
- Scenes/Performance;
- Song/Composition;
- UI-V2 visual system;
- generic Pattern↔Melody demotion;
- multi-level Undo history.

Those belong to later checkpoints, especially M-ACCEPT and M-UX1.

## RED acceptance contracts

Implementation begins only after tests demonstrate the current violations or characterize existing behavior. The minimum behavioral contract set is:

1. Pattern edit changes WORKING, not Scene canonical data.
2. All untouched `SynthPattern` fields survive Working edits losslessly.
3. Sounding runtime reflects Working Pattern content.
4. Undo/Redo changes WORKING only.
5. DISCARD reconstructs WORKING from ACCEPTED.
6. Recovery/autosave still serializes ACCEPTED A while runtime auditions Working B.
7. Pattern→Melody Working conversion leaves canonical descriptor Pattern.
8. Conversion uses Working Pattern B, not stale ACCEPTED Pattern A.
9. LENGTH growth preserves existing bar-1 musical content exactly at the representation boundary.
10. Melody Working behavior remains equivalent to the existing `currentPhrase_` runtime contract.
11. Modified/not-modified is derived rather than maintained as an independent dirty truth.
12. Switching material target with modified Working cannot silently destroy it.
13. `sizeof(WorkingMaterialStorage) <= sizeof(RuntimeSynthEventBuffer)`.
14. Cardputer static DRAM does not increase relative to the agreed base budget.
15. Existing ACTIVE/NEXT causality and failed-preparation behavior remain unchanged.

## STOP conditions

Stop before production implementation if evidence shows any of the following:

- lossless Pattern Working cannot fit by reusing current Melody buffer ownership;
- implementation requires a second canonical representation truth;
- exact Working/Accepted distinction cannot be established without mutating persistence;
- the storage refactor increases static DRAM beyond the release budget;
- Pattern→Melody conversion cannot preserve existing Working musical content;
- an existing runtime owner makes the proposed storage union unsafe for simultaneous use.

In those cases the design must be reopened rather than patched around.

## Final invariant

The musician edits a musical idea. Pattern and Melody are implementation representations selected by capability. ACCEPTED is durable truth; WORKING is the mutable candidate; runtime is a projection/publication of WORKING. Representation changes must never masquerade as musical acceptance.
