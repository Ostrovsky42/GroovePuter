# Rhythm Browser catalog checkpoint — RB-103/104 subset

Base: `e4b17df269ecbbb69a7b4c8996edbc27350f414e`. This is a control-side catalog and candidate factory; it does not add an on-device screen, start playback, send MIDI, change Scene or implement Apply/Undo.

## Catalog and deterministic materialization

`RhythmBrowser::descriptorAt` enumerates the current 24 reference IDs and the six compiled Atlas recipes, each identified by `(source, stableId)` so namespaces cannot collide. Human-readable names, actual variant count, 4/4 eligibility, BPM hints, provenance and a `RequiresMaterialization` renderability state are returned without changing the project. The descriptor alone does not claim a playable candidate: each request must first materialize successfully. Atlas descriptors explicitly retain `CompiledAtlasRightsReview`: existing compiled material is not proof of redistribution rights. Vocabulary entries expose only the one technically audited generic P1 realization; no claims are made for P2/P3. Atlas names, BPM and variant counts come from the generated runtime metadata rather than a second copied catalog.

`matchesGroup` reuses the existing base-genre compatibility data for HOUSE, TECHNO, UKG, HIP-HOP, ACID and ELECTRO. BREAKS maps to Drum & Bass and DUB to Reggae compatibility as preliminary filters; Atlas 6–7 map to ACID, 8–9 to UKG, 10–11 to DUB. ALL includes every known descriptor. This does not modify Genre or prevent cross-genre selection. The grouping and names require musician review; in particular, generic drum-only realization intentionally ignores tonal roles, so a name such as Chord Response must not be advertised as verified musical content without listening.

The caller supplies `Workspace` and `Candidate`. The identity contains source, stable ID, variant, fixed preview seed and context version. Vocabulary invokes the existing realizer and materializer with explicit ignored tonal roles; Atlas uses the existing drum-only extractor. A failed lookup, variant, realization or empty result returns a typed status without changing the output candidate. Seed is preserved in Atlas identity but does not affect its drum steps. The context version is carried, not checked against the live owner; a later audition/apply transaction must validate it. Scratch groove and automation are defaults, not user state; future preview/apply must preserve the accepted project settings.

## Memory boundaries

With the installed Xtensa ESP32-S3 toolchain (`-std=c++17 -Os`), compile-time type sizes are `Workspace=1,416 B`, `Candidate=1,208 B`, and `RhythmRealizationResult=628 B`. `-fstack-usage` reports the factory's own frame as 752 B, `materializeRhythmPattern` as 1,536 B and `realizeRhythmPhrase` as 176 B. These are individual static frames, not a complete call-chain maximum or a device high-water measurement. Workspace and candidate lifetime, double-buffer needs, ownership and the 5,700-byte provisional baseline DRAM margin must be audited before integrating playback. No allocation, I/O, serialization or catalog scan has been added to the audio ISR.
