## Hardware evidence

The runtime + audio block histogram image was uploaded to ESP32-S3 rev 0.2 (MAC `d8:85:ac:a4:4b:ec`). `esptool.py` reported successful writes and verified the written data hash. After the hard reset, the USB serial/JTAG device did not re-enumerate. A 60-second reconnect-safe monitor run therefore captured only reconnect retries; no boot, audio, heap, stack, or MIDI runtime measurements were obtained. The host no longer reports an Espressif USB device. Kernel logs were unavailable to this process (`dmesg` permission denied).

The user reported an earlier 30-minute successful run. Its exact firmware SHA, scenario, MIDI route, and raw log are unavailable. This is recorded as user-reported qualitative soak evidence; the 30-minute run will not be repeated. It does not prove zero underruns, MIDI delivery, heap stability, or SEQTRAK acceptance.

A separate 60-second capture dated 2026-11-18 showed audio underruns at zero during the observed PLAY interval, but its firmware identity is unknown. In that capture USB-MIDI had 275 endpoint-busy rejections out of 292 attempts, one demotion, and a reported 2,873 ms maximum blocked interval; MIDI dispatch reported 138 clock drops, 25 transport failures, 66 late events, and 24,435 μs maximum lateness. DIN reported 183 bytes sent and zero NoteOn/NoteOff drops. Because firmware identity and route are unknown, this is a historical diagnostic lead, not evidence for the current `8bfc5b81` image or proof of physical delivery.
